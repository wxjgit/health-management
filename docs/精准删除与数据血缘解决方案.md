# 精准删除与数据血缘解决方案

本文是针对当前 SQLite、LangGraph 实现的设计方案，尚未实施业务代码改造。

## 1. 目标和约束

删除一条 event 或 fact 后，清除它本身及所有相关副本、派生内容和恢复入口；保留能够证明独立的健康记录、聊天和流程。

必须同时满足：

1. 删除范围可解释，执行前可以预览。
2. 已删除内容不残留在消息、卡片、通知、旧修订或 checkpoint 中。
3. 模型晚到结果、旧请求重试、进程重启都不能恢复已删除内容。
4. 独立对象保持内容、状态和可恢复性。
5. 依赖未知时扩大清理范围，但不能静默扩大用户已经确认的范围。

保持当前单进程、本地单数据集架构；使用 SQLite 表和递归遍历，不引入图数据库。现有 `engine.lock` 仍负责本地串行提交，不宣称支持多进程部署。

## 2. 当前问题定位

| 位置 | 当前行为 | 改造方向 |
|---|---|---|
| `repositories/events.py::delete_event` | 删除目标后调用无参数 `erase_context()` | 由统一删除服务计算并执行范围 |
| `api/profile.py::delete_fact` | 忽略是否存在，无条件全清 | 不存在时无副作用；与 event 走相同服务 |
| `repositories/maintenance.py::erase_context` | 对多张表执行无条件 DELETE | 保留为显式兜底入口，禁止默认调用 |
| `workflows/runtime.py::purge_checkpoints` | 删除所有 thread，增加全局 epoch | 正常删除仅清理受影响 thread |
| `workflows/concurrency.py` | 使用全局 epoch、全局数据版本保护 | 增加流程代次、实际读取集合校验 |
| `repositories/common.py::_bump` | 数据版本增加时让所有 active insights 失效 | 分离版本计数与依赖失效，仅更新相关来源/范围 |
| `evidence/binding.py::ground_event` | 每个事件保存来源消息全文 | 保存最小证据片段，登记共享原文副本 |
| `health/planning.py::plan_draft` | 读取 30 条事件、facts 等，只展示 12 条引用 | 展示引用与实际依赖分开 |
| `jobs/scheduler.py` | 已完成任务不会因为结果被删自动重跑 | 精准失效任务产物，按需生成新版本 |

不能简单把全局 DELETE 改成 `WHERE evidence_refs LIKE ...`：引用不完整，字符串匹配也无法覆盖嵌套对象、原文共享和历史版本。

## 3. 数据模型：三种关系分别记录

### 3.1 展示引用

保留 `evidence_refs`，只用于 UI 展示。可以裁剪数量，但不能参与“依赖已完整”的证明。

展示尽量按当前有效来源解析，减少保存原文快照。必须保存的快照应登记为副本。

### 3.2 计算依赖

统一维护来源到产物的依赖边。例如：

```text
event:E1@v1 → insight:I1@g1 → review:R1@g2 → notification:N1@g1
fact:F1@v1 → plan:P1.schedule@g1
plan:P0.targets@g2 → plan:P1.targets@g1
```

这里 `version` 是来源自己的版本，`generation` 是产物的生成版本，不能仅使用全局 `data_version`。

对计划等混合对象，至少将 `targets` 和 `arrangement` 分成两个血缘部件；必要时继续拆分。只有部件有独立完整依赖时，才允许只清理部分内容。

建议新增：

```text
provenance_nodes
  node_id                内部唯一 ID
  object_type            event/fact/message/plan/insight/review/notification/...
  object_id              业务对象 ID
  object_version         版本或生成代次
  part                   whole/targets/arrangement 等
  provenance_state       complete/unknown
  lifecycle              live/stale/deleting/deleted

provenance_dependencies
  source_node_id
  target_node_id
  relation               derived_from/context_read
```

约束与索引：

- 对象类型、ID、版本、部件组合唯一。
- 依赖边组合唯一，来源列和目标列分别建索引。
- 删除时按照逻辑来源 ID 查找所有版本，避免只清最新版本。
- 来源删除后暂时保留不含业务内容的节点标记，不能立即级联删除依赖索引而丢失清理依据。
- 对每次生成使用不可变版本，避免同一个 insight ID 更新后，旧通知被误认为依赖最新内容。

派生对象可返回 `source_event_ids`、`source_fact_ids` 和版本列表，便于调试；这些是依赖表的投影，不另维护一套权威数据。

### 3.3 内容副本

依赖关系不能覆盖“跑步事件中藏着体重原文”这种情况，还要登记敏感内容存放在哪里：

```text
provenance_occurrences
  subject_node_id         被复制内容所属的来源
  holder_node_id          保存副本的对象及版本
  field_path             如 data.evidence_sources[0].text
  occurrence_kind        source_span/structured_copy/opaque_text
  locator                已验证片段位置或结构字段位置
```

消息 `M1` 产生 E1、E2 是来源关系，不应直接解释为“删除 E1 就删除 M1 产生的所有事件”。删除规划器需要检查 M1 及其所有副本是否包含 E1 内容，处理副本后保留独立的 E2。

索引只保存 ID、类型和位置，不复制原文。片段定位不能依赖一次普通字符串替换：位置必须和持有对象版本绑定。

## 4. 在生成时登记完整依赖

新增 `ProvenanceContext`，由本地代码记录实际输入，不要求模型自行声明依赖。

```python
with provenance.capture(thread_id) as context:
    # 业务函数仍决定读取范围；跟踪仓储登记输入节点和查询范围。
    plan = plan_draft(context.repo, targets)
    repo.save_plan_with_provenance(plan, context.dependencies)
```

要求：

1. 业务对象及其节点、依赖边、副本记录在同一业务库事务提交。
2. 写入后的对象才对外可见，不能先保存内容、后异步补依赖。
3. facts 增加版本；profile、preferences、完整日标记、计划目标等也提供版本化来源。
4. 复盘嵌入 insight 时，登记对该 insight 生成版本的依赖；通知复制复盘摘要时同理。
5. workflow result、receipt、消息 cards、重试 payload 和所有 checkpoint 状态都属于存储面，不能只登记最终回复。
6. 运行中已经读取的来源，在释放锁进行模型 I/O 之前登记到流程依赖中。
7. 对 `limit`、时间窗口、筛选和空结果查询，额外登记查询范围依赖。否则新增数据、删除候选记录或修改完整日标记时，旧结果仍可能被错误认为有效。

`_bump()` 当前会无条件使所有规律 stale，也需要拆开。保留全局版本号用于缓存或兼容，并不意味着继续使用它决定所有产物失效；精准失效必须按照变化的来源及查询范围进行。

第一版可以保守地把业务函数实际读取的记录全部记为依赖。随后通过缩小查询和拆分部件减少误伤，不能通过省略依赖来缩小删除范围。

`complete` 表示生成链路、原文副本和恢复存储均已覆盖。`evidence_refs=[]` 或没有查到依赖边，不能证明对象独立。

## 5. 共享原文和历史修订处理

以“今天体重 65 公斤，跑步 20 分钟”为例：

```text
E1：体重事件
E2：跑步事件
M1：同时包含两条记录的原始消息
```

删除 E1 时：

- 删除 E1 及其全部 revisions、来源 facts。
- 删除或脱敏包含体重的 M1、回复、卡片、receipt 等副本。
- 如果 E2 的 `evidence_sources` 保存 M1 全文，将其改为已验证的跑步证据片段，重新计算哈希、字符范围和来源标识。
- 同样检查 E2 的旧 revisions，不能仅修改最新 `data`，让旧修订继续藏着体重。
- 检查 `raw_text`、feedback、纠错来源等其他字段；不能假设只有 `evidence_sources` 会复制整句消息。
- 能证明独立时保留 E2 的跑步业务内容；不能证明时，不拼接或猜测新证据，应在预览中扩大到该共享来源组。

后续新记录改为保存最小、可验证的来源片段。片段外的原始消息如果继续保留，也必须作为受管理的副本登记，而不是移到另一张表后视为问题已解决。

清除敏感内容后，使用无内容占位对象保留必要状态，例如“此结果因来源删除已失效”。仅设置 `status='stale'` 却保留旧正文，不算完成隐私删除。

## 6. 删除服务和执行协议

新增 `PrivacyDeletionService`，event、fact、归档中的隐私清理均调用它；区分用户删除与保留策略归档，归档摘要的保留规则需显式登记。

### 6.1 删除预览

建议接口：

```text
POST /api/deletions/preview
  { target_type, target_id }

POST /api/deletions
  { preview_id, request_id }

GET /api/deletions/{deletion_id}
```

预览返回：目标、将删除/脱敏/失效的数量、受影响流程、保留对象、清理范围、扩大原因和服务端保存的范围令牌。

执行时重新计算范围。范围若超出预览中用户确认的边界，返回 `409 scope_changed` 和新预览，不静默执行更大范围。使用精确依赖、共享来源组、未知历史上下文、全局上下文等明确边界，不只比较数量。

现有 `DELETE /events/{id}`、`DELETE /facts/{id}` 应接入同一个服务，不能保留一条可绕过范围检查的全清路径。正式前端切换后，首次有效删除要求提供预览令牌；重复删除已完成目标返回无副作用结果，未知目标返回 404。

### 6.2 持久化删除作业

新增：

```text
deletion_jobs
  deletion_id, request_id, target_type, target_id
  scope_token, state, created_at, completed_at

deletion_items
  deletion_id, object_locator, action, state

request_tombstones
  request_id, request_kind, state, deletion_id
```

`deletion_items` 存定位信息和动作，不保存待删除正文。受影响请求的删除标记只保留必要 ID 和状态，不保存原请求、结果或可直接复原敏感信息的摘要。

执行步骤：

1. **锁内校验并建立屏障。** 验证目标和预览；持久化作业，将来源标为 deleting，提升受影响流程的代次。此后所有读取、导出、恢复和写入入口必须拒绝使用被屏障覆盖的内容。
2. **计算闭包并提交业务清理。** 沿计算依赖、内容副本、线程所属存储和嵌套产物遍历，清理目标所有版本；生成请求删除标记和 checkpoint 待办。动作与业务数据更新在同一业务库事务内提交。
3. **清理 checkpoint。** 按受影响 thread 调用 `delete_thread()`，包括历史 checkpoint 和 saver 管理的待写状态。第一版不手工修改 LangGraph 内部序列化结构。
4. **更新任务产物。** 使受影响的 daily/weekly/通知作业结果过期；仍满足条件时，用新的生成代次重算。保留无关作业和通知去重状态。
5. **完成物理维护并确认。** 确认没有可访问的正文副本和恢复入口；完成当前两个数据库的 WAL/页清理策略后，才将作业标为 completed。

业务库和 checkpoint 库不能用一个普通 SQLite 事务完成原子提交，因此依靠“持久化屏障 + 幂等作业”保证恢复一致性。服务启动必须先恢复屏障、执行未完成清理，再开放受影响数据和 scheduler。失败时保持屏障、返回 pending/failed，不能返回删除完成。

SQLite 清理应检查锁和 WAL checkpoint 的实际结果，失败可重试；不要仅凭已执行 `VACUUM` 就宣称成功。应用只能覆盖自身数据库及受管存储，用户外部导出的文件不在该协议中。

## 7. 不让旧请求和并发结果写回

### 7.1 流程代次

将正常删除使用的全局 `context_epoch` 拆为持久化流程代次 `workflow_generation`；全局 epoch 仅用于真正的全局清理。

每个运行实例携带：

```text
thread_id
workflow_generation
实际来源 ID 和版本
查询范围版本
```

进入节点、模型调用返回、保存业务对象、保存 workflow result/receipt，以及 saver 写 checkpoint 前，都在锁内验证这些信息与来源删除状态。代次不一致或来源删除时抛出 `WorkflowConflict`。

现有 `_model_context_version()` 和 `decide_plan()` 的全局数据版本校验也要逐步替换成完整依赖校验。未完成依赖登记的链路继续保守校验，不能提前宣称独立流程完全不受影响。

### 7.2 旧请求重放

收到旧 chat/resume 请求时，先查 `request_tombstones`，再决定是否创建 workflow 或读取 receipt。受删除影响的旧请求返回 `410 request_erased`，不重新执行。

独立线程正常重试，独立 operations 的幂等记录保留；受影响 operations 仅保留必要拒绝重放标记。删除作业自身使用 request_id 幂等，重复执行不会扩大清理范围。

请求删除标记不能随普通聊天保留期一起清除。只要服务仍接受该旧请求 ID，就必须保留拒绝重放能力；如需限制标记规模，应先定义并强制执行请求有效期，不能直接到期删标记。

主动重新输入相同内容并使用新请求 ID 属于新的用户操作；本方案防止系统自动恢复，不承诺识别用户再次主动提供的同一事实。

### 7.3 模型调用预算

目前 `model_calls` 只保存 purpose、字节数和时间，不保存健康原文。不能为了清理某条记录而重置所有独立流程的预算；受影响线程按既定保留策略处理即可。

## 8. 对象处理策略

| 对象 | 处理策略 |
|---|---|
| event、来源 fact、revisions | 删除目标及全部相关版本 |
| 消息、cards、process trace | 能可靠局部清除则脱敏，否则删除受影响消息；清理浏览器中旧副本 |
| workflow、receipt、resume payload、checkpoint | 第一版以受影响 thread 为最小恢复单位整体清理，保留无正文删除状态 |
| insight、review、notification | 清除旧内容并失效，条件仍成立时生成新版本 |
| plan.targets | 仅完整证明来源独立时保留；继承的目标递归追踪来源 |
| plan.arrangement | 受影响时清除，保留可独立证明的目标并提示重建安排 |
| jobs | 精准失效相关产物，不全表重置 |
| monthly_summaries | 登记来源集合；若删除范围包含聚合贡献，重算或删除受影响月摘要 |
| profile、preferences、weight_history 等 meta | 登记来源；只有明确复制目标内容或存在派生关系时处理，不凭数值相等推断依赖 |

用户确认过计划不等于其派生目标已经独立。只有用户明确作为独立手动目标提供，且实际数据链路可证明独立时，才允许保留。

## 9. 旧数据迁移与兜底

迁移不调用模型猜测依赖，也不自动删除当前数据库。

1. 给旧对象默认标记 `unknown`。
2. 从 source_event、thread_id、record_ids、完整证据字段、明确嵌套关系恢复能够证明的边和副本定位。
3. `evidence_refs` 只作为已知依赖的下限，不能把补到了部分边的对象标记 complete。
4. 对未知对象逐级扩大：已知依赖闭包 → 共享来源/相关 thread → 无法证明独立的历史上下文 → 全部上下文。
5. 如果保留事件或旧 revisions 中仍有共享原文，必须处理这些副本；沿用当前 `erase_context()` 并不能解决这一点。
6. 无法独立保留的基础事件需要在预览中明确列出，用户确认扩大后才删除，不能以“全局上下文清理”为名静默删除其他健康事件。

全局兜底也应走持久化删除协议，保留旧请求拒绝重放能力。随着新生成链路覆盖完整，兜底比例应逐步下降。

## 10. UI 行为

精确清理示例：

> 将删除这条体重记录，并清理 2 条消息、1 份趋势结果和 1 个相关流程。共享消息中的体重片段也会清除，跑步记录保留。

扩大清理示例：

> 部分历史上下文缺少完整来源关系，无法确认是否保存了此记录。需要清理这些历史上下文及全部流程进度；其他能够独立保留的健康记录保留。展开查看影响范围。

必须显示实际后端预览，不使用固定的“相关内容已清理”文案代替范围说明。删除期间显示处理中，完成后刷新消息、流程、计划、通知和报告，清除 React 状态及其他标签页中受影响的缓存；不保留含原文的撤销副本。

## 12. 实施顺序

### 阶段一：先修确定性问题

- 不存在的 fact 删除不再清理其他对象。
- 增加删除作业和请求删除标记，阻止旧请求重建数据。
- 现有全清文案明确说明“全部”，同时列出活跃计划的保留与清空范围。
- 补上共享原文和旧 revisions 的检测，避免把当前全清当作已完成彻底删除。

### 阶段二：先铺血缘，再切换删除

- 增加节点、依赖、副本和版本模型。
- 完成业务产物、线程存储、来源片段和运行中读取的同步登记。
- 影子运行删除规划器，核对影响范围；此阶段不因“有了部分字段”就开启精确模式。

### 阶段三：上线精准清理

- 上线预览、分阶段作业、流程代次保护和启动恢复。
- 仅 provenance complete 的链路启用精准保留，未知对象使用明确兜底。
- 前端切换并更新旧测试中“所有上下文必须清空”的断言。

### 阶段四：收敛历史兜底和无关失效

- 完成旧数据迁移、聚合摘要、任务重算和查询范围失效。
- 逐步替换全局模型上下文版本检查；在可靠覆盖前保留保守检查。
- 记录不含正文的作业计数、兜底原因和失败状态，用于定位尚未覆盖的链路。

## 13. 验收标准

| 场景 | 必须验证的结果 |
|---|---|
| 删除一个 event，另有独立聊天和待补充流程 | 目标及相关副本删除；独立消息、receipt、workflow、checkpoint 保留且可恢复 |
| 删除不存在的 fact；重复删除同一目标 | 无关数据零变化，不触发全清 |
| 一条消息同时生成体重和跑步事件 | 体重从全部副本、旧修订和导出消失；可独立验证的跑步记录保留 |
| 删除计划展示引用以外但实际用到的事件 | 计划相关部件仍被识别并清理 |
| review 嵌入较早 insight，通知复制 review | 间接副本和各生成版本均清理 |
| 删除发生在模型 I/O 期间 | 相关晚到结果不能写回；独立流程仍可提交 |
| checkpoint 后台写入与删除并发 | 不留下可重放旧状态 |
| 删除后重发原 chat/resume request_id | 返回 request_erased，不创建事件或回复 |
| 业务清理后、checkpoint 清理前崩溃 | 重启先恢复屏障，再完成清理；期间不能读到旧内容 |
| 删除预览后依赖范围扩大 | 返回新预览，不静默扩大执行 |
| daily/weekly 产物失效 | 允许按新代次重算；独立任务去重状态保留 |
| 历史对象 provenance unknown | UI 明确扩大原因，按确认的范围执行 |
| WAL 清理失败或数据库忙 | 作业不误报 completed，可恢复重试 |

验收需要同时检查 API、导出、业务数据库各正文列、revisions、checkpoint 历史和浏览器状态；不能只检查事件列表。使用唯一测试标记定位受测内容，检查与原文无关的 ID/统计标记时应明确区分。

最终完成条件是：目标内容及其副本已清理、恢复入口被封闭、无关上下文可继续使用，且删除范围与用户看到并确认的范围一致。
