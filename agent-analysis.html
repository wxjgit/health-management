State 状态字段字典

State 是三个 Graph 共用的 TypedDict(total=False)：字段缺席表示“尚未设置”，不等于空值。节点只返回本次修改的字段；普通列表没有 reducer，不会自动追加，需复制旧列表后再返回。checkpoint 保存的是流程执行状态，不是健康事实源，也不授予模型外发权限。

43 个声明字段一个字段一行chat / plan / analysis 共用thread_id 级 checkpoint
字段类型 / 初值语义生产者消费者 / checkpoint 生命周期
CallScope.grants / approved / disclosures仅存在于一次 Engine.invoke 的内存调用域，用于授权、批准与披露；不会写入 Graph checkpoint，也不能在恢复流程时被复用。
model_calls是 health.db 中的模型调用审计与预算账本，不是 State 字段；记录用途、预算、状态和摘要，不保存完整请求正文。
__interrupt__由 LangGraph 运行时在中断结果中投影，供 format_result 读取交互载荷；它不是 State 中声明的业务字段。
01

处理计划与数据 Harness

按当前源码核对：计划审批与外发授权是两层检查；包括首次 plan 在内，每次模型请求都经过同一个出口。图为节点内部调用关系，不新增 Graph 节点。

图上两处检查指的是同一个 ModelBoundary。PlanHarness 负责规划审批与引用绑定；补丁、营养、表达和建议分别在其业务节点构造资源，所有请求最后都走 Parser.request → approve → model_request → consume → HTTP。查询结果不送模型作二次总结；若另有 advice 任务，其上下文独立按批准视图构造。

建议的六种固定视图

程序根据原文复核并选择；不是模型自己决定最终取数范围
最终获批不读历史none只有 question / scene / view / now；无健康历史。注意：计划默认 none 可能被程序按问题补成相关视图，见下方范围规则。
单餐指代meal_reference仅绑定一餐，最多 10 个食物；不带其他餐食、全天汇总或反馈。仍含下述饮食共用字段。

近期饮食汇总diet_week最多 7 天，只列有餐食记录日期的餐数、营养汇总与完整性；无逐餐列表。明确更短窗口就缩短；含饮食共用字段。

饮食共用字段：meal_reference / diet_today / diet_week / diet_portion 都可能带 active_targets（四项营养目标）、constraints（最多 8 条）、preferences（最多 5 条）、nutrition_context 与固定 selection_policy。每条长期信息最多 500 字符。none 与 weight_trend 不带这些字段。证据 ID 和旧聊天原文不放入建议 context；单条纠错 / 补丁的投影仍可含目标记录 / 当前草稿的 raw_text，不能概括为“所有模型调用都不发送 raw_text”。

范围如何决定当前工程的实际规则
模型申请 data_viewapprove_plan 根据当前原文重算相关视图，可以补全默认 none，或把单餐指代收窄成 meal_reference；不接受不相关的视图申请。用户明确要求不读历史时，只接受 none，不自动补成历史视图。
时间窗口diet_week ≤ 7 天，weight_trend ≤ 28 天；明确更短就缩短，本周按已过天数。上周、上个月、去年等不支持窗口与超上限请求直接拒绝，不偷偷扩成默认窗口。单日数据按 question 解析日期；字段 today 不一定是今天。
本地查询 query模型只提结构化查询条件，Repository 在本地执行，最多返回 100 条；类型与关键词受原文检查，同时给出起止时检查范围为 0–365 天。不是把这 100 条再交给模型总结。
语义与写入边界原文锚定、Schema 与范围规则能拒绝已覆盖的越界情况，不是任意自然语言的语义证明。模型只返回计划或草稿，健康事件仍需后续本地校验、准备和 Repository 写入。
每 thread_id ≤ 4 次规划每 thread_id ≤ 32 次调用预记账每次业务 JSON ≤ 90,000 UTF-8 字节累计业务 JSON ≤ 400,000 字节进入网络阶段后的失败 / 重试也计入

字节预算按序列化的业务 payload（user JSON，含 task / Schema 等）计算，不是 token 数，也不是包括 system 提示词、模型名和 HTTP 头在内的完整请求大小。consume 在连接建立前持久化预记账；未通过此前审批的请求不会记成已外发。预算按 thread_id 跨暂停、重试与重启累计；新工作流不是同一份预算。

指代与纠错选中记录优先；否则原话须命中指代规则或以“不是”开头，才按需查同会话上轮引用，且必须唯一。目标不明时，prepare_clarification 最多给出 5 条本地候选；候选列表不发给模型。
暂停与恢复增量补充走 patch_pending，不重新规划；合并范围由 pending 字段控制，纠错复核绑定版本。advice_context 取数前重审保存的建议 action；不能统称“恢复后所有计划都重审”。CallScope 每次 invoke 新建，checkpoint 不保存可复用授权。

例

Harness 专题 · 一次“65kg 改成 66kg”怎样被约束

场景、实际代码与数据范围放在一起看 · 按 2026-10-21 当前实现核对。

核心不是让模型自己遵守“少看数据”，而是程序先装好允许发送的数据，再审核模型提出的任务。下面是假设模型正确识别纠错意图时的代码推演，不读取真实健康记录，也不代表已经执行过一次模型请求。代码片段省略了无关分支。

用户实际怎么说

先记录：

今天体重65kg。

系统已保存，随后用户发现说错了：

不是，刚才那条改成66kg。

本地有什么，但不该一并交给模型

假设数据库还有昨天的餐食、睡眠与其他日期的体重。此次没有手动选中记录；同会话上一轮只有刚保存的那条体重结果。

第一轮规划不查、不发送上轮结果数量；只有后面确实需要解析“刚才那条”时，才在本地读取引用元数据。

当前修改要求→① 模型只提计划→本地审批 / 绑定目标→② 模型只改这一条→后续校验 / 保存

  1. 先让模型听懂这句话，不告诉它旧体重

    parse_initial 把工作交给 self.harness.prepare(state)。在模型模式下，Harness 先登记允许发送的内容，再调用规划模型：

    self.parser.boundary.grant('processing_plan', {
    'text': state['input_text'],  # 不是，刚才那条改成66kg。
    'interaction': {'selected_record': bool(selected)}  # False
})
plan = self.parser.plan(state['input_text'], bool(selected))

    模型实际接收的业务内容如下；请求还会附加当前时间、固定任务名与输出 Schema：

    {
  "text": "不是，刚才那条改成66kg。",
  "interaction": {"selected_record": false}
}
    这一关限制的是“第一次能看到什么”：模型不知道原来是65kg，不知道上轮结果数量，也看不到餐食、睡眠或历史聊天正文。grant 只是登记本次允许发送的内容，不是给模型一个查库工具。
    代码定位：harness.py · PlanHarness.prepare

  2. 模型提出“纠错”，程序先检查这张申请单

    假设模型提出一项 correct，text 是当前原话，target=previous、events=[]、data_view=none。这不是可直接执行的命令，必须先经过 actions = self.approve_plan(state, plan)：

    if action.text not in state['input_text']:
    raise PolicyError('处理计划必须对应本次输入，不能自行扩展问题。')
if action.intent != 'record' and action.events:
    raise PolicyError('规划阶段只有新增任务可以携带事件草稿。')
if action.data_view != 'none' and action.intent != 'advice':
    raise PolicyError('此任务不能申请建议数据。')
    这一关限制的是“能申请做什么”：纠错不能夹带模型编出的旧事件，也不能顺带申请一周饮食数据。原文匹配和字段规则是本地检查，但不是对自然语言理解正确性的完整证明。
    代码定位：harness.py · PlanHarness.approve_plan

  3. “刚才那条”由本地程序定位，不由模型选择 ID

    模型说 target=previous 本身不构成授权。resolve 优先使用用户选中的记录；没有选中时，检查的是用户当前原话，然后才按需读取同会话上一轮的引用：

    selected = self.selected(state)
if selected:
    return selected
if REFERENCE.search(state['input_text']) or state['input_text'].startswith('不是'):
    ids = self.previous_ids(state)
    if len(ids) == 1:
        return self.repo.event(ids[0])
return None

    代入本例：原话有“刚才那条” → 查询上一轮引用 → 只有一条体重记录 → 在本地读取原值65kg。如果上一轮有体重和睡眠两条，无法唯一确定，则不进入单条纠错模型调用：

    prior = self.resolve(state, correction)
if not prior:
    return ExtractionResult(
        intent='correct',
        question='要修改哪条记录？请先选择记录，或明确上一轮记录。'
    ), [], actions
    这一关限制的是“究竟操作谁”：唯一目标由本地引用和用户选择确定。真实记录 ID 留在程序中；目标不明确就返回追问，后续走澄清流程，不把更多历史交给模型猜。
    代码定位：harness.py · resolve / previous_ids / prepare

  4. 第二次才给原记录，而且只给绑定这一条的必要字段

    确定目标后，record_projection 按固定字段裁剪记录，排除数据库 ID、版本、无关反馈与营养派生元数据。然后为“本次修改要求 + 这份投影”单独授权：

    projection = record_projection(prior)
self.parser.boundary.grant('correct_selected', {
    'text': correction.text,
    'record': projection
})
updated = self.parser.correct(correction.text, projection)

    此时模型才知道：原记录是今天体重65kg，用户要改成66kg。餐食、睡眠和其他体重没有被一起放进去。模型返回后，类型和原日期还受程序控制：

    if updated.event.kind != prior['kind']:
    raise PolicyError('纠错不能改变记录类型，请另建记录。')
updated.event.occurred_at = datetime.fromisoformat(prior['occurred_at'])
    这一关限制的是“给哪份历史、允许怎样修改”：只给已绑定记录的投影；修改结果不能换类型，日期强制沿用原记录。上述类型 / 日期检查位于 if updated.event: 分支；模型也可以返回需要补充的问题。
    代码定位：harness.py · record_projection / prepare 的 correct 分支

  5. 两次模型调用，都必须经过同一个外发门卫

    这一关发生在每次 HTTP 请求之前，不是等第二次纠错结束后才检查。grant 登记内容指纹，approve 校验用途、字段、固定 Schema 与实际数据，再将请求固定为不可变内容：

    grant = self._grant_key(purpose, self._resource(purpose, data))
if grant not in scope.grants:
    raise PolicyError('发送内容没有通过本次处理计划的范围检查。')
scope.grants.remove(grant)

    例如：授权的是“修改要求 + 体重记录”，后续却夹带餐食，会被字段检查或内容指纹检查拒绝。通过审核后，传输层还要消费一次性批准：

    # Parser.request
call = self.boundary.approve(purpose, data)
return self.model_request(prompt, call, output_type)

# Parser.model_request：通过后才建立 HTTP 连接
data = self.boundary.consume(call)
    这一关限制的是“最终实际发了什么”：未授权、改了内容、重复使用批准、纯本地模式或预算不足，都会在该次网络请求发出前拒绝。授权由可信本地构造代码创建，不是由模型返回的 JSON 创建；它不替代前面的业务范围审批。
    代码定位：harness.py · ModelBoundary.grant / approve / consume
    网络出口：parser.py · request / model_request

同一个案例，两次模型调用究竟各看到了什么

阶段模型可见仍留在本地 / 不附带
第一次：processing_plan当前原话、selected_record=false、时间、固定任务与 Schema。上轮结果数量、引用 ID、原体重65kg、历史正文；此时不查询上轮引用元数据。
本地审批 / resolve不是一次模型调用。按需读取同会话上轮引用；只有唯一目标才读取该记录。用户选中记录优先。
第二次：correct_selected当前修改要求、原体重记录的必要字段投影、时间、固定任务与 Schema。真实记录 ID / version、其他记录、历史聊天、无关反馈与营养派生元数据。
返回 parse_initial不会因为返回草稿就再发送全量历史。本地绑定 correction_id / version，返回 extraction；后续 normalize_extraction → validate_drafts → prepare_nutrition → save_ready → persist → respond，按条件路由；缺信息则先 clarify。

走不通时，在哪一关停下

发生什么当前实现怎么处理
模型正确提出纠错，但上轮有多条结果resolve 不返回唯一目标；prepare 生成问题，不调用 correct。
纠错计划夹带事件草稿或申请饮食视图approve_plan 抛 PolicyError；不执行该纠错模型调用。
模型改成了其他记录类型纠错模型已经调用，但返回结果被本地拒绝；不能直接写库。
发送前请求夹带额外记录或内部字段ModelBoundary 字段或指纹校验失败；该次 HTTP 请求不发出。
用户选择纯本地模式Parser.mode 变为 local，prepare 使用本地解析分支；边界层同时禁止创建 / 使用模型外发授权。本例的“两次模型调用”不适用。
模型没有识别成纠错，或把66理解错这些规则不能保证语义一定正确。新增 / 纠错混合等已覆盖情况会澄清，但不能承诺所有误分类都会被识别；数据最小化也不等于数值理解正确。

一句话串起来：模型理解“想改成66kg” → 程序决定“改哪条” → 模型只接收那条记录 → 出口核对实际内容 → 后续节点校验并保存。parse_initial 形成草稿，不直接写健康事件；Harness 约束数据访问，但不是对模型语义正确性的保证。

继续阅读：PlanHarness 完整实现说明 · ModelBoundary 授权生命周期 · parse_initial 的输入输出 · 固定视图与累计预算。

六类调用逐项说明

“阻断”表示失败会返回 409；“可降级”表示主流程仍可完成
parse_initial 节点 · 首轮规划plan()
失败阻断
触发model 模式下的新聊天；记录、纠错、查询、咨询、长期事实都先经过它。
输入now / text / interaction / schema；interaction 只有 selected_record 布尔值；不查询或发送上轮结果数量。
输出ProcessingPlan.actions：1–4 个 record / correct / query / advice / fact / clarify 任务。
复核PlanHarness 检查原文、申请视图、范围与指代；纠错计划不得包含记录 ID 或旧事件草稿。
失败请求、JSON 或 Schema 任一失败 → ValueError → workflow failed → HTTP 409；不切 demo。
parse_initial 节点 · 绑定单条纠错目标后correct()
失败阻断
触发correct 任务已有选中记录，或明确指向同会话上轮唯一结果；否则先追问。
输入text / record_projection / now / schema；一条记录的必要字段，没有 ID 或数据库元数据。
输出CorrectionResult：event 或 question；不允许模型返回其他记录 ID。
复核程序绑定 ID、类型、原日期与版本；落库前再核验版本，防止覆盖补充期间的修改。
失败解析失败返回 409；目标不明确提供最多 5 条本地候选，不向模型发送候选列表。
patch_pending 节点 · resume 补充patch()
失败阻断
触发clarify 恢复后需要真正补字段时；取消、不知道或转为咨询由本地逻辑处理，不调用。
输入本次回答 / 当前草稿投影 / requested_fields / item_index / now / schema
输出EventPatch：只允许待补字段及本轮 feedback，不返回完整事件。
复核merge_patch 只合并白名单字段；不能改已知日期和食物，也不能用历史记录补空缺。
失败模型或结构化输出失败 → HTTP 409；已有草稿仍由 checkpoint 管理。
prepare_nutrition 节点estimate_nutrition()
可降级
触发准备保存的 meal 有明确食物和实际分量，但热量或三大营养素仍缺失。
输入name / quantity / unit / size / cooking / requested_nutrients / provided_nutrients
输出NutritionEstimates：按 item index 返回缺失数值与 uncertainty。
复核索引唯一、用户值优先、描述指纹匹配；热量与宏量能量差超过 max(50 kcal, 35%) 就拒绝。
失败食物和分量照常保存；缺失营养保持 unknown / partial，并写明失败原因，不按 0 处理。
prepare_clarification / respond 节点phrase_reply()
可降级
触发本轮存在 salty / oily / overeating / hungry 反馈，且本地 make_plan 产生批准要点。
输入plan.points / feedback 标签 / stage / context.foods[:3] / boundary / schema；不读取历史聊天。
输出ContextualReply：每个 segment 必须保留 point_id，只负责自然表达。
复核点位与顺序完全一致；检查主题锚点、长度、数字、日期、保存状态、诊疗和新增建议。
失败使用本地 ACK / GUIDANCE 原文；医学或钠边界由程序追加，记录写入结果不受影响。
respond 节点 · 普通咨询answer_advice()
可降级
触发intent=advice，且不是医疗边界、保存回执、查询或 feedback-only 路径。
输入仅批准的视图：单餐、指定日期、≤7 天饮食、≤28 天体重或分量档案；历史聊天原文不发送。
输出AdviceReply.answer：直接回答重点，最多两条可执行建议。
复核禁止上下文外数字、诊疗结论、把不完整记录说成全天结论、把剩余额度说成必须吃满。
失败按同一个 context 生成 fallback_advice；不会将失败回答写成事实或事件。
