SAFETY ROUTING · 先判断能不能做，再决定怎么做

一句“晚饭吃多少”，为什么要先过安全检查？

“记录午饭”和“催吐后还想减肥”都在谈饮食，处理方式却不同。现在请求先经过本地规则和独立 LLM 分类，再由程序决定是否允许继续估算、给建议或生成计划。本节对照当前安全实现，前面的总览保留原业务链路快照。

修复背景：旧程序为什么可能把身体不适当成普通饮食问题？

问题来自《架构与安全 Review 建议》中的“医疗安全边界”检查。原来已有 medical_question()，但它只识别少量关键词，而且主要在回复阶段的部分分支使用。安全判断没有成为所有入口共同的前置检查。

“我头晕，晚饭吃多少？”

这句话同时包含身体不适和饮食咨询。旧正则没有“头晕”这个词，检查返回 False；代码便缺少一条强制停止普通建议的边界。低血糖、持续腹泻、催吐、未成年人和孕产期复杂问题，也存在类似的覆盖缺口。

原因一：关键词没命中，就缺少明确拦截 
# 修复前已有的检查 · 等价分行展示
def medical_question(text):
    return bool(re.search(
        r'血压|高血压|糖尿病|肾病|肾功能|心脏|胸痛|呼吸困难|'
        r'持续.*(?:痛|吐)|用药|吃药|药量|利尿|排盐|排毒',
        text
    ))

medical_question("我头晕，晚饭吃多少？")
# False：没有匹配到关键词

只增加几个词仍会留下隐晦表达，例如“吃完把东西弄出来”。因此增加独立 LLM 分类，负责理解这些语义。

原因二：检查位置靠后，部分业务已经能够执行
解析输入parse_initial→ 准备营养、保存prepare_nutrition / persist→ 生成回复respond

respond 的部分分支才调用医疗关键词检查；已保存记录的分支会组装营养说明与餐食评分，额外建议任务还有自己的执行路径。末尾的一句能力提示，不能阻止前面的估算、评分或附加建议。

混合请求尤其容易暴露这个问题：“记录午餐，另外我持续腹泻”；追问时突然补充不适，以及从计划入口提交目标，也需要共同的安全边界。

这次修复要达到的效果：先判断能否进入普通链路，命中风险就用本地固定策略结束；模型判断后、实际操作前和回复输出前继续检查。首次输入、追问及计划入口采用同一边界。

旧路径对照修复前提交 df50bb4。这里说明代码允许的漏判路径，不代表旧模型每次都会给出同样回答。medical_question() 仍保留为局部回复辅助，新的主安全入口已放到它之前。背景来源：架构与安全 Review 建议 · 3.5

档案是什么？

用户明确提供的年龄、孕哺状态和医疗限制。它们是本地检查的依据；这一版没有另建长期“未解除风险”表，也不自动保存诊断。

模型说不清，怎么办？

超时、预算耗尽、非法结构或原文证据不匹配，都转为 uncertain。本地固定回复说明边界，已经保存的独立记录保留并说明。

没有模型，还能记录吗？

仅允许完整匹配离线白名单的记录、查询和明确食物偏好；不补演示营养、不评分、不附带建议。其他自由输入使用保守边界。

LLM 的“普通”不是医学安全证明。 本地规则与模型都有覆盖范围，输出检查也不是医学事实验证器。一次 16 条合成语料实测中，10 条风险均被拦截、6 条普通均放行，但有 2 条首选风险分支与标注不同；平均分类约 3.9 秒。这是小样本验证，不代表生产召回率或临床验证。

按当前源码核对：计划审批与外发授权是两层检查；包括首次 plan 在内，每次模型请求都经过同一个出口。图为节点内部调用关系，不新增 Graph 节点。

图上两处检查指的是同一个 ModelBoundary。PlanHarness 负责规划审批与引用绑定；补丁、营养、表达和建议分别在其业务节点构造资源，所有请求最后都走 Parser.request → approve → model_request → consume → HTTP。查询结果不送模型作二次总结；若另有 advice 任务，其上下文独立按批准视图构造。

核心不是让模型自己遵守“少看数据”，而是程序先装好允许发送的数据，再审核模型提出的任务。下面是假设模型正确识别纠错意图时的代码推演，不读取真实健康记录，也不代表已经执行过一次模型请求。代码片段省略了无关分支。

用户实际怎么说

先记录：

今天体重65kg。

系统已保存，随后用户发现说错了：

不是，刚才那条改成66kg。

本地有什么，但不该一并交给模型

假设数据库还有昨天的餐食、睡眠与其他日期的体重。此次没有手动选中记录；同会话上一轮只有刚保存的那条体重结果。

第一轮规划不查、不发送上轮结果数量；只有后面确实需要解析“刚才那条”时，才在本地读取引用元数据。

当前修改要求→① 模型只提计划→本地审批 / 绑定目标→② 模型只改这一条→后续校验 / 保存

  1. 先让模型听懂这句话，不告诉它旧体重

    parse_initial 把工作交给 self.harness.prepare(state)。在模型模式下，Harness 先登记允许发送的内容，再调用规划模型：

    self.parser.boundary.grant('processing_plan', {
    'text': state['input_text'],  # 不是，刚才那条改成66kg。
    'interaction': {'selected_record': bool(selected)}  # False
})
plan = self.parser.plan(state['input_text'], bool(selected))

    模型实际接收的业务内容如下；请求还会附加当前时间、固定任务名与输出 Schema：

    {
  "text": "不是，刚才那条改成66kg。",
  "interaction": {"selected_record": false}
}
    这一关限制的是“第一次能看到什么”：模型不知道原来是65kg，不知道上轮结果数量，也看不到餐食、睡眠或历史聊天正文。grant 只是登记本次允许发送的内容，不是给模型一个查库工具。
    代码定位：workflows/policy.py · PlanHarness.prepare

  2. 模型提出“纠错”，程序先检查这张申请单

    假设模型提出一项 correct，text 是当前原话，target=previous、events=[]、data_view=none。这不是可直接执行的命令，必须先经过 actions = self.approve_plan(state, plan)：

    if action.text not in state['input_text']:
    raise PolicyError('处理计划必须对应本次输入，不能自行扩展问题。')
if action.intent != 'record' and action.events:
    raise PolicyError('规划阶段只有新增任务可以携带事件草稿。')
if action.data_view != 'none' and action.intent != 'advice':
    raise PolicyError('此任务不能申请建议数据。')
    这一关限制的是“能申请做什么”：纠错不能夹带模型编出的旧事件，也不能顺带申请一周饮食数据。原文匹配和字段规则是本地检查，但不是对自然语言理解正确性的完整证明。
    代码定位：workflows/policy.py · PlanHarness.approve_plan

  3. “刚才那条”由本地程序定位，不由模型选择 ID

    模型说 target=previous 本身不构成授权。resolve 优先使用用户选中的记录；没有选中时，检查的是用户当前原话，然后才按需读取同会话上一轮的引用：

    selected = self.selected(state)
if selected:
    return selected
if REFERENCE.search(state['input_text']) or state['input_text'].startswith('不是'):
    ids = self.previous_ids(state)
    if len(ids) == 1:
        return self.repo.event(ids[0])
return None

    代入本例：原话有“刚才那条” → 查询上一轮引用 → 只有一条体重记录 → 在本地读取原值65kg。如果上一轮有体重和睡眠两条，无法唯一确定，则不进入单条纠错模型调用：

    prior = self.resolve(state, correction)
if not prior:
    return ExtractionResult(
        intent='correct',
        question='要修改哪条记录？请先选择记录，或明确上一轮记录。'
    ), [], actions
    这一关限制的是“究竟操作谁”：唯一目标由本地引用和用户选择确定。真实记录 ID 留在程序中；目标不明确就返回追问，后续走澄清流程，不把更多历史交给模型猜。
    代码定位：workflows/policy.py · resolve / previous_ids / prepare

  4. 第二次才给原记录，而且只给绑定这一条的必要字段

    确定目标后，record_projection 按固定字段裁剪记录，排除数据库 ID、版本、无关反馈与营养派生元数据。然后为“本次修改要求 + 这份投影”单独授权：

    projection = record_projection(prior)

    'text': correction.text,
    'record': projection
})

    此时模型才知道：原记录是今天体重65kg，用户要改成66kg。餐食、睡眠和其他体重没有被一起放进去。模型返回后，类型和原日期还受程序控制：

    if updated.event.kind != prior['kind']:
    raise PolicyError('纠错不能改变记录类型，请另建记录。')
updated.event.occurred_at = datetime.fromisoformat(prior['occurred_at'])
    这一关限制的是“给哪份历史、允许怎样修改”：只给已绑定记录的投影；修改结果不能换类型，日期强制沿用原记录。上述类型 / 日期检查位于 if updated.event: 分支；模型也可以返回需要补充的问题。
    代码定位：modeling/projections.py · record_projection
    纠错分支：workflows/policy.py · prepare

  5. 两次模型调用，都必须经过同一个外发门卫

    这一关发生在每次 HTTP 请求之前，不是等第二次纠错结束后才检查。grant 登记内容指纹，approve 校验用途、字段、固定 Schema 与实际数据，再将请求固定为不可变内容：

    grant = self._grant_key(purpose, self._resource(purpose, data))
if grant not in scope.grants:
    raise PolicyError('发送内容没有通过本次处理计划的范围检查。')
scope.grants.remove(grant)

    例如：授权的是“修改要求 + 体重记录”，后续却夹带餐食，会被字段检查或内容指纹检查拒绝。通过审核后，传输层还要消费一次性批准：

    # Parser.request
call = self.boundary.approve(purpose, data)
return self.model_request(prompt, call, output_type)

# Parser.model_request：通过后才建立 HTTP 连接
data = self.boundary.consume(call)
    这一关限制的是“最终实际发了什么”：未授权、改了内容、重复使用批准、纯本地模式或预算不足，都会在该次网络请求发出前拒绝。授权由可信本地构造代码创建，不是由模型返回的 JSON 创建；它不替代前面的业务范围审批。
    代码定位：modeling/boundary.py · ModelBoundary.grant / approve / consume
    网络出口：modeling/parser.py · request / model_request

提取 Grounding Harness · 模型给候选，本地证明原文

它不判断模型“有多自信”，而是重做原文绑定，并在写库前把证据完整重放一遍。

实际输入与错误候选

今天吃了100g苹果和200g香蕉
# 模型把数量归属对调
苹果 → 200g（quote="200g"）
香蕉 → 100g（quote="100g"）

本地运行结果

苹果 → 100g · span 4..8
香蕉 → 200g · span 11..15

source.text[11:15] == "200g"

代码第六步 · 最后的几项登记，要么一起保存，要么一起不保存

假如程序只记下“流程成功”，还没记下“请求 A 已成功”就崩溃，重启后这些登记就对不上了。因此 finish_resume() 把下面四项放进同一个数据库事务。

# Repository · finish_resume()（结构示意，省略 SQL 参数）
with self.lock, self.conn:
    # 1. 更新 workflow 状态和结果
    # 2. 保存 receipts：请求 A 已成功，以及上次的结果
    # 3. 标记 resume_attempts：这次答案处理已完成
    # 4. 保存助手回复

self.lock 让这些受保护的数据库操作按顺序进行；self.conn 管理数据库事务，成功一起提交，中途异常则回滚这一组修改。计划取消也将“计划拒绝”和“流程取消”一起提交。

如果只是成功回复在网络上丢了，原请求重试时，_resume_receipt() 找到成功凭据后直接返回上次结果，不再执行 Graph。但这个事务只覆盖最后的登记，不会自动撤销前面节点已经保存的健康记录，也不包含另一个数据库里的 Graph 存档。

对应代码：Repository · finish_resume() / cancel_workflow()；成功结果复用：runtime.py · _resume_receipt()。

同一 health.db 事务

finish_resume() 将 workflow 结果、成功 receipt、attempt 完成标记和助手回复一起提交。cancel_workflow() 将待确认计划拒绝与 workflow 取消一起提交。内部使用不自行提交的消息插入函数，避免嵌套方法提前提交。workflow、receipt、messages 和 plans 的查询也获取 Repository 锁，防止同一 SQLite 连接读到尚未提交的中间值。

不宣称跨数据库整体回滚

先补基础：checkpoint 是什么，为什么删除记录还要管它？

这里有三样不同的东西：业务数据、流程存档、删除任务记录。checkpoint 就是“流程存档”，类似游戏存档：程序中断后，可以知道之前做到哪里、接下来做什么。

今天体重65公斤，请帮我分析一下。
① 保存体重记录 E1
        ↓
② 读取最近的体重变化
        ↓
③ 请求模型生成分析
        ↓
④ 保存分析结果
        ↓
⑤ 给用户发送通知

这整个任务叫一个 workflow（流程），这里编号为 W1。checkpoint 保存它执行过程中的状态，例如：

    }
}

checkpoint 不只记录“执行到了第几步”，也可能保存任务用过的数据、对话和模型结果。所以业务表里的 E1 删掉了，流程存档里可能还留着“65公斤”和相关分析；仅删除业务记录，隐私副本可能仍然存在。

对象可以理解成什么例子
业务数据用户正式保存的记录和结果E1：体重65公斤，以及相关聊天、分析等。
checkpoint任务的执行存档W1 做到哪一步、用过的数据和中间结果。
删除任务记录删除操作的工单清理哪些对象、哪些流程，以及清理到哪个阶段。

W2 是什么？它只是另一次任务的编号，例如根据 E2 跑步记录生成运动建议、正在等待用户补充信息的流程。只要没有使用 E1，且来源可以证明独立，删除 E1 时就应该保留 W2 的消息、等待状态和存档。

⑤ 防写回：从所有流程一起失效，到相关流程代次失效

白话讲解：删掉存档，为什么任务还能把旧数据写回来？ 
W1 读取 E1：体重65公斤
        ↓
W1 把数据发给模型，等待返回
        ↓
用户删除 E1，系统也删除 W1 的 checkpoint
        ↓
模型返回分析结果
        ↓
如果没有额外检查，旧 W1 又把分析结果保存回数据库！

删除存档，不等于停止正在运行的程序。程序内存里可能还拿着旧数据，模型请求也可能还没有结束。就像你销毁了桌上的文件，但同事之前已经拿走一份，稍后又把处理结果放回桌上。

所以还要检查：这次任务是否仍然有资格继续写入？原来所有任务共用一个全局版本号，删除时这个号码一变，W1 和无关的 W2 都会失效；全量清理 checkpoint 又把两者的存档一起删除。

现在每个流程单独保存一个 generation，可以理解成执行凭证的版本号。假设 W1 和 W2 启动时都拿到自己的第1版凭证：

W1：体重分析E1数据库版本1，运行任务持有版本1。数据库变成版本2，旧任务仍拿着版本1，拒绝继续写入。
W2：独立跑步任务E2，没有使用 E1数据库版本1，运行任务持有版本1。版本仍为1，通过其他必要检查后可以继续。

if 数据库里的流程版本 != 任务启动时的版本:
    拒绝旧任务继续写入

代码中 with repo.conn: 包住的重点是：业务清理与工单更新为 checkpoint_pending，在健康数据库的同一个事务里完成。它们一起提交，或者一起回滚，避免“业务清完了，却没记下下一步”。

工单 D1：business_pending
        ↓ 业务清理与阶段更新，一起提交
工单 D1：checkpoint_pending
        ↓ 假设这时清理存档失败，程序退出
工单仍保存在数据库，状态没有丢
        ↓ 用户重试，或者服务重启恢复
读取 D1，继续处理剩下的 checkpoint 和存储清理
        ↓ 全部成功
工单 D1：completed

中途失败时返回 pending、deleted=False，意思是整个删除任务尚未完成，并不表示前面的业务删除一定没有发生。这两个数据库仍然不是一个事务；改进在于跨库操作中断后，系统有可靠的记录继续完成，不会假报成功或忘掉剩余工作。

白话讲解：request_tombstones 为什么还要保留请求编号？

旧数据还有另一种回来方式：客户端重新发送了之前的请求。这和正在运行的模型任务写回，是两个不同入口。

请求 R1：创建体重记录 E1
        ↓
服务端创建成功，但客户端没收到响应
        ↓
用户从其他页面删除 E1
        ↓
客户端重试 R1
        ↓
如果没有作废登记，系统可能又把 E1 创建一遍

request_tombstones 可以理解成一张“作废登记”：请求 R1 已因隐私删除而作废，不允许重新执行。它不保留体重正文，只保留拦截重放所需的请求标识等信息。

机制它负责挡住什么
checkpoint 清理清掉已经保存的流程副本。
流程代次 generation拦住正在运行的旧任务继续写入。
删除工单 deletion job记录未完成工作，让中断的清理可以继续。
请求作废登记 request_tombstones拦住旧请求重试，避免重新创建已删除的数据。
