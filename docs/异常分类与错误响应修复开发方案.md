# 异常分类与错误响应修复开发方案

> 前端已迁移为微信小程序，网络实现为 `miniprogram/src/api.ts`，不再启用浏览器开发 CORS。本文保留原 Web 阶段设计记录；当前运行与验证方式见 [微信小程序开发方案](微信小程序开发方案.md)。

日期：2026-10-27

状态：已实施并通过回归；实现差异、异常审计及验证结果见第 13 节。

对应问题：《架构与安全Review建议》5.3「模型错误不应统一映射成 409」。

## 1. 问题与修复目标

当前存在以下调用链：

```text
模型连接失败 / 超时 / 上游 HTTP 失败 / 返回格式错误 / Schema 校验失败
  → modeling/parser.py 包装为 ValueError
  → main.py 的 ValueError 处理器
  → HTTP 409 + {"detail": str(error)}
```

业务参数不合法、版本冲突、流程状态失效也使用 `ValueError`，因此客户端无法判断应修改输入、刷新状态还是稍后重试。未知的 `ValueError` 也会被误判为业务冲突。

其他已确认的缺口：

- 普通 409 和兜底 500 没有稳定错误码，也没有请求追踪 ID。
- 409 直接返回异常字符串，无法保证未来异常不包含健康原文、上游内容或密钥。
- FastAPI 默认请求校验响应可能在 `detail[].input` 中回显健康输入。
- 前端部分逻辑通过中文错误文案判断冲突，修改提示语可能改变行为。
- 现有 `test_model.py` 明确断言模型格式错误返回 409，需要同步修正测试预期。

修复目标是：按错误来源分类，统一脱敏响应，提供可追踪的请求标识，并保持现有持久化、幂等和局部降级语义。

## 2. 范围与约束

本次修改包含后端异常、API 错误处理、请求追踪、前端错误消费及对应测试，无数据库结构迁移。

约束：

1. 保留当前成功响应结构、流程恢复协议、请求去重和并发保护。
2. 保留明确的本地处理模式；模型失败不能自动切换演示解析或编造营养数值。
3. 安全分类失败仍进入保守安全回复；营养、建议和回复表达的已有局部降级继续有效。
4. 未知程序错误返回 500，不能被宽泛捕获后包装成业务错误或模型故障。
5. 不修改现有 request_id、receipt、resume_attempt 和删除凭据的存储语义。
6. 本期不新增自动重试、后台补偿任务或对外发送日志的服务。

## 3. 异常层次与状态码

新增 `backend/app/common/errors.py`，放置不依赖 FastAPI、httpx 和数据库的公共异常及错误码注册表。

```text
AppError(Exception)
├── DomainValidationError              → 422
├── ConflictError                      → 409
│   ├── WorkflowStateError             → 409
│   └── WorkflowConflict               → 409，保留现有类与导入路径
│       └── RequestErased              → 410，保留专用处理
└── ModelError
    ├── ModelUnavailableError          → 503
    └── UpstreamModelError             → 502

未识别的 Exception，包括普通 ValueError、TypeError → 500
```

异常分类用于表达原因，API 层负责 HTTP 映射；领域服务和仓储不直接抛 `HTTPException`。错误码属于固定注册表，不从异常文案、模型输出或客户端输入动态生成。

建议的最小错误码集合：

| 异常或入口 | 稳定错误码 | HTTP | 典型场景 |
| --- | --- | --- | --- |
| 请求 Schema 校验 | `request_validation_failed` | 422 | 必填字段缺失、字段类型不合法 |
| DomainValidationError | `domain_validation_failed` | 422 | 事实内容与用户明确填写的对象不一致 |
| DomainValidationError | `policy_scope_denied` | 422 | 用户操作超出当前允许的数据范围 |
| ConflictError | `request_payload_conflict` | 409 | 相同业务 request_id 对应不同请求内容 |
| ConflictError | `resource_version_conflict` | 409 | 记录、事实或计划依据的版本变化 |
| WorkflowStateError | `workflow_state_invalid` | 409 | 当前流程已没有待回答问题 |
| WorkflowStateError | `workflow_interrupt_changed` | 409 | 提交的 interrupt 已失效 |
| WorkflowConflict | `workflow_execution_conflict` | 409 | 执行中取消、并发执行或过时工作 |
| WorkflowConflict 的明确场景 | `plan_confirmation_in_progress` | 409 | 计划正在确认，无法取消 |
| ModelUnavailableError | `model_unavailable` | 503 | 连接失败、连接/读取/写入超时、本地连接池暂不可用 |
| ModelUnavailableError | `model_rate_limited` | 503 | 上游返回 429 |
| ModelUnavailableError | `model_service_unavailable` | 503 | 上游明确返回 503 |
| UpstreamModelError | `model_upstream_failed` | 502 | 上游 401/403、其他未单独映射的非成功状态 |
| UpstreamModelError | `model_response_invalid` | 502 | 上游响应缺少 choices、content 类型错误、JSON 或 Schema 不符合协议 |
| UpstreamModelError | `model_output_rejected` | 502 | 模型提出伪造记录 ID、越界数据视图或不受原文支持的结果 |
| 未知异常 | `internal_error` | 500 | 程序缺陷、未分类的 ValueError/TypeError |

这里的 502/503 是本项目的接口约定：网络可达性、超时、限流及上游明确不可用归 503；其他上游调用失败或响应不符合契约归 502。不要直接把上游状态码透传给用户，例如供应商 401 不代表本应用用户需要重新登录。

`ModelUnavailableError` 只有在操作明确需要模型、且模型能力无法提供时使用；不把用户选择本地处理模式视为故障。

### 3.1 异常携带的数据

`AppError` 仅携带注册过的 `code`，以及按该错误码约束的安全结构化字段。展示文案来自后端固定表，不接受任意 `public_message=str(error)`。

示意：

```python
raise ConflictError(code='request_payload_conflict')
raise ModelUnavailableError(code='model_unavailable') from error
```

`from error` 可以保留进程内因果关系，但不得因此自动输出完整异常链。未知错误码、错误类与注册状态码不匹配，应被视为内部错误，统一返回 `internal_error`。

### 3.2 现有特殊异常的兼容

- `WorkflowConflict` 改为公共冲突异常的子类，保留 `workflows/concurrency.py` 中的类名和导入路径。修改所有抛出点为固定 code，不能继续以任意字符串作为公开内容。
- `RequestErased` 继续返回 410 和现有 `request_erased` code；其处理优先于父类 409。
- `DeletionError` 保留当前 404、409、422、428 等状态、现有 code 和 `preview` 字段，并通过统一响应构造器补充请求标识。
- `DeletionError` 的 code/status 组合也应列入白名单，detail 使用对应固定文案，不能任意返回构造函数 message。
- 继续允许删除错误的安全预览元数据：`target_type`、`target_id`、`counts`、`scope`、固定原因和 `preview_id`。禁止加入健康原文、事实 content、记录 raw_text 或内部 manifest。

### 3.3 PolicyError 与 GroundingError 必须按来源拆分

当前 `PolicyError(ValueError)` 同时覆盖用户范围限制、模型结果越界和本地授权异常，不能整体机械映射为 422。

| 来源 | 目标分类 |
| --- | --- |
| 用户明确提交不支持的范围或不合法字段 | DomainValidationError，422 |
| 模型输出未经授权的字段、伪造 ID、扩展本次问题或不支持的证据 | UpstreamModelError，502 |
| 正常并发或流程恢复使授权依据失效 | ConflictError / WorkflowStateError，409 |
| 本地代码错误地复用一次性模型授权、构造错误内部调用协议 | 内部异常，500 |

逐个审计 `modeling/boundary.py`、`modeling/payloads.py`、`workflows/policy.py`、`chat_parsing.py` 和 `chat_flow.py` 的抛出点，必要时为内部授权不变量定义内部异常，但不为其增加公开业务状态码。

`GroundingError` 同理：模型证据不受原文支持时，由对应模型结果校验边界转换为 `model_output_rejected`；内部来源登记冲突等不变量错误仍为 500。不能给所有 GroundingError 统一贴上“上游故障”标签。

## 4. 统一错误响应

继续保留前端已使用的 `detail` 字段，增加 `code` 和 `request_id`：

```json
{
  "detail": "模型服务暂时不可用，请稍后重试。",
  "code": "model_unavailable",
  "request_id": "2de982e0-7bdc-4e8b-9f7d-af035a6e1ae1"
}
```

响应头同时返回：

```text
X-Request-ID: 2de982e0-7bdc-4e8b-9f7d-af035a6e1ae1
```

规则：

- 所有应用生成的 API 4xx/5xx，包括路由 404、方法 405、隐私清理 503、410、428 和未知 500，都使用同一基础结构。
- 稳定 code 用于程序判断，detail 用于用户展示；修改中文文案不改变客户端分支。
- 成功响应仅增加响应头，不修改业务 JSON。
- 删除流程可以额外返回上述经过白名单过滤的 `preview`。
- 422 可额外返回安全 `errors`，其他错误不携带任意异常属性。
- 不承诺统一接管请求尚未到达应用时的连接失败、反向代理错误或响应已经发送后的异常。

### 4.1 请求校验错误脱敏

为 FastAPI `RequestValidationError` 增加专用处理器。不要直接返回 `exc.errors()` 或 `exc.body`。

```json
{
  "detail": "请求参数不合法，请检查后重试。",
  "code": "request_validation_failed",
  "request_id": "2de982e0-7bdc-4e8b-9f7d-af035a6e1ae1",
  "errors": [
    {"field": "text", "code": "invalid_value"}
  ]
}
```

仅从接口 Schema 已知字段名和本地错误类型映射出 `field/code`，限制条数和字段长度。未知字段名使用固定占位名，不回显任意输入键、值、URL、Pydantic ctx、原始 msg 或 input。列表索引可采用受限数字路径，不能携带用户提交的字典键。

客户端响应模型校验失败或内部手工调用 Pydantic 失败，不得自动当成客户端输入错误。模型输出校验仅在模型边界转为 502；其他未分类的内部校验失败归 500。

### 4.2 HTTPException 和未知异常

注册 Starlette `HTTPException` 处理器，覆盖路由层 404/405 以及 FastAPI 抛出的 HTTPException。

- 已知接口错误使用固定 code/detail；保留必要的受控协议响应头，例如 405 的 Allow。
- 没有业务 code 的标准 HTTP 错误使用稳定的 `http_<status>`，例如 `http_404`；提示来自本地状态码表。
- 不直接返回任意 `HTTPException.detail` 或任意附加 headers。
- 未知异常一律返回 500 + `internal_error` + 固定提示，不输出 `str(error)`、repr、SQL、堆栈或异常链。
- 删除 `@app.exception_handler(ValueError)`，不能用另一层宽泛的 `except ValueError` 重新制造原问题。
- 内部响应 Schema 错误也采用上述 500 脱敏策略。

## 5. request ID 与幂等键

本方案明确区分两个概念：

| 标识 | 来源和用途 | 重试行为 |
| --- | --- | --- |
| 请求体 `request_id` | 现有业务幂等键，关联 workflow、receipt、resume_attempt 或删除任务 | 相同操作重试复用原值 |
| 响应 `request_id` / `X-Request-ID` | 服务端生成的本次 HTTP 尝试追踪 ID | 每次 HTTP 尝试生成新值 |

两者同名属于现有业务字段与新错误信封的不同层次，必须在代码注释和前端类型中说明。前端将错误追踪字段命名为 `ApiError.requestId`，不能写回业务请求体。

实现要求：

1. 请求入口生成 UUID，不依赖请求体，也不接收客户端自定的追踪 ID。本期忽略入站 `X-Request-ID`，避免无效字符、伪造和敏感内容进入日志。
2. 在解析请求体前写入 `request.state.request_id`，确保非法 JSON、缺少字段、GET/DELETE 和 404 也有 ID。
3. 设置请求上下文 ContextVar，供同步路由、模型适配器和安全日志读取；退出请求时在 finally 复位，避免串号。
4. 所有错误处理器从 request.state 获取 ID，并显式写入响应头与响应体，不能仅依赖正常响应中间件补头。
5. 未知异常可能在外层错误中间件处理；即使 ContextVar 已复位，仍应从 request.state 获取正确 ID。共用响应构造器须接受显式 ID。
6. CORS 配置暴露 `X-Request-ID`；本期无需允许客户端发送该头。验证来自当前两个允许 Origin 的 500 响应也具有可用 CORS 头，不能只验证普通 409。若默认中间件层次使 500 绕过 CORS，调整 CORS 包装层级并保留 FastAPI lifespan、state 和测试依赖注入入口。
7. 后台定时任务使用独立的受控任务关联信息，不能继承上一次 HTTP 请求 ID。

## 6. 模型适配器改造

将 `Parser.model_request()` 拆成四个责任明确的阶段，限定捕获范围：

```text
本地批准与消费授权
  → 构造固定请求
  → 发起模型 HTTP 调用并分类传输/状态错误
  → 校验上游响应协议、JSON、输出 Schema
```

### 6.1 传输与 HTTP 状态

- `httpx.TimeoutException`、连接/网络故障、连接池暂时不可用：`model_unavailable`，503。
- 上游 429：`model_rate_limited`，503。
- 上游 503：`model_service_unavailable`，503。
- 其他非成功状态：`model_upstream_failed`，502。请求仍禁止自动跟随重定向，3xx 不能成为新的发送目标。
- 若添加 Retry-After，仅允许对 429/503 使用本地规定范围内的合法秒数；不能直接透传任意供应商响应头。
- 本地请求构造、序列化或配置不变量导致的未知错误归 500，不伪装成模型服务暂不可用。

### 6.2 响应协议与输出

依次验证响应是合法 JSON 对象、choices 为非空列表、message 为对象、content 为字符串，再执行当前 Markdown 包裹清理及输出 Schema 校验。

响应 JSON 解码失败、协议形状错误和该阶段 Pydantic ValidationError，转换为 `model_response_invalid`，502。建议显式检查类型，不用包住整段函数的 KeyError/TypeError/AttributeError 捕获掩盖本地程序缺陷。

Schema 合法但模型结果越界，例如伪造目标 ID、证据不在本次原文、选择未批准的建议项，由消费结果的窄校验入口转换为 `model_output_rejected`，502。

普通 TypeError、AttributeError 等只有在明确验证上游值的窄边界内才可被判定为协议错误；其他位置自然进入 500。

### 6.3 工作流和隐私异常不转换

授权审批、授权消费以及 `network_context` 可能发现取消、删除或版本变化。`WorkflowConflict`、`RequestErased` 必须原样向上传播，不能转成 ModelError，也不能触发模型降级后继续写入。

不改变现有模型调用计数、发送前授权、外发范围白名单、禁用重定向和调用预算。

## 7. 业务抛出点与局部降级改造

### 7.1 按语义迁移业务异常

| 当前位置/情形 | 目标 |
| --- | --- |
| runtime：同一业务 request_id 对应不同内容 | ConflictError / `request_payload_conflict` |
| runtime：没有待回答问题、interrupt 变化 | WorkflowStateError / 对应稳定 code |
| runtime：答案缺失、需要接受或拒绝但参数未给出 | DomainValidationError / 422 |
| facts/events：expected_version 不匹配、纠错期间版本变化 | ConflictError / `resource_version_conflict` |
| facts：内容与对象/取值不一致、临时期限不合法 | DomainValidationError / 422 |
| planning：采用的默认目标指纹已变化 | ConflictError / `resource_version_conflict` |
| planning：标成系统默认的提交值与当前默认不一致 | DomainValidationError / 422 |
| safety：用户明确提出的目标不满足当前能力限制 | DomainValidationError / 422，使用固定提示 |
| safety：确认阶段资料变化使原安全判断失效 | WorkflowStateError 或版本冲突 / 409 |
| 数据库版本不兼容、内部持久化不变量错误 | 内部错误；启动时明确失败，HTTP 处理中为 500 |

资源不存在的处理沿用相应接口已有 404 契约；对“已经不存在或版本已变化”的合并场景按原并发冲突语义保留 409。不要为统一异常分类顺便改变所有资源查询接口语义。

### 7.2 局部降级捕获必须同步修改

新异常不继承 ValueError 后，旧的 `except (ValueError, TypeError)` 将无法捕获模型故障。以下四处必须同时迁移：

| 文件/入口 | 模型故障后的既有目标行为 |
| --- | --- |
| `workflows/safety.py` / classify_safety | 标记 classifier_failed，进入 uncertain 的本地安全回复，不继续普通处理 |
| `health/nutrition.py` / prepare_nutrition | 保留用户食物、分量和营养输入，缺失估算保持未知，允许已有流程完成 |
| `chat/replies.py` / express_plan | 使用同一批准要点的本地表达 |
| `workflows/chat_response.py` / advice | 使用同一受控上下文的本地建议兜底 |

这些位置捕获 `ModelError` 和明确命名的结果校验失败异常。局部校验若仍使用 Pydantic ValidationError，可在只包含结果校验的窄范围捕获；随后逐步用专用输出校验异常替代。

不能继续用大范围 ValueError/TypeError 捕获包住本地上下文构造、数据库操作或持久化；未知缺陷应上抛到 500。演示模式选择本地回复改为显式分支，不再通过人工抛 ValueError 表示正常控制流。

HTTP 502/503 仅适用于无法由该操作既有降级策略完成的模型错误。安全风险分类的失败仍可返回成功的保守工作流响应；不能因为换异常类而放宽安全判断或把所有降级改成 HTTP 失败。

## 8. 前端行为

修改 `frontend/src/api.ts`：

- `ApiError` 保留 status、code、preview，增加可选 `requestId`。
- 优先读取响应头 `X-Request-ID`，其次使用经过 UUID 格式校验的错误体 request_id；不将其用于业务幂等。
- 优先消费新的字符串 detail；短期兼容旧数组 detail 和无 JSON 的失败响应。
- 错误提示可显示「请求编号：…」以便排查；不展示异常对象 JSON、上游详情或密钥。
- 网络断连或代理返回非 JSON 时使用本地通用提示，不伪造服务端 request ID。

修改 `frontend/src/App.tsx`：

- 计划取消的“正在确认”分支使用 `code === 'plan_confirmation_in_progress'`，替换 `message.includes('计划正在确认')`。
- 同步版本发布后由 code 决定业务分支；兼容旧后端时只保留有限的通用提示，不长期依赖文案判断。
- 422 引导修改输入；409 引导刷新或恢复现有流程；502/503 提示模型服务异常并允许用户手动重试；500 提示处理失败和请求编号。
- 修改输入或重新选择资源后创建新的业务 request_id；原样重试同一操作继续复用原业务 request_id、interrupt_id 和原答案。
- 错误状态不代表事务一定没有提交。计划确认仍查询实际状态，沿用当前去重和确认恢复逻辑；不能因收到 500/502/503 就自动重新生成一个请求执行。

## 9. 安全日志

记录最小字段：服务端 request_id、稳定错误码、HTTP 状态、受控 operation/purpose、异常类型、耗时；上游状态码可作为纯数字记录。

禁止输出：请求体、健康原文、模型 prompt、原始 response body、Authorization、API key、完整 URL/query、SQL 参数、str/repr(error)、未过滤的异常链和局部变量。日志路由使用固定模板，例如 `/api/workflows/{thread_id}/resume`，不直接记录可能带用户内容的完整路径。

统一处理器和局部降级使用同一安全日志函数。不要默认 `logger.exception()`、`exc_info=True` 或输出 cause 的 message。确需定位未知 500 时，可额外记录仅包含代码文件、函数和行号的栈帧元数据，不包含源码行、变量值和异常字符串。

保留异常链只供进程内调试；生产日志默认不序列化。该限制也适用于测试失败信息、工作流 process_trace、错误持久化结果及后台任务。

## 12. 完成条件与交付

开发完成时必须满足：

- 必需模型步骤的传输/协议故障可通过 503/502 与 409 区分。

- 日志及错误持久化的模拟敏感标记扫描通过。
- 交付代码、错误码表、测试结果，以及剩余 ValueError/PolicyError 的审计清单；文档状态由待实施更新为实际验收结果。

本次发布需协调前后端错误契约。新增字段兼容旧版通用 detail 消费，但 409 调整为 422/502/503 会改变现有状态码依赖，属于需要明确告知的行为修复；不应仅以“新增字段向后兼容”描述整个改动。


## 13. 实施结果与异常审计

### 13.1 已完成的实现

- `common/errors.py`：公共异常、固定错误码/文案和错误类校验。未知错误码或错误类与错误码不匹配时归 500。
- `api/errors.py`：统一处理领域错误、未知错误、请求校验、框架 HTTP 错误、删除错误和已擦除请求；禁止异常字符串透传。
- `api/request_context.py`：保留 FastAPI 对象的 state、lifespan 和依赖注入入口，在默认错误中间件外围接入追踪及 CORS。成功/失败请求和 CORS 预检均分配服务端 UUID，非法预检也返回安全错误信封。
- 请求追踪中间件仅在统一 500 响应已经完整发送后，终止 Starlette 对该异常的再次传播，避免 ASGI 服务输出原始异常链。响应尚未完成、流式发送失败或未由安全处理器接管的异常继续传播；取消等 BaseException 不被吞掉。
- `modeling/parser.py`：分离传输故障、上游状态、返回协议和模型 Schema 校验；取消/删除检查继续在受保护的模型 I/O 上下文退出时生效。
- `common/safety_messages.py`：从原安全模块原样提取固定帮助文案；`SafetyPolicyError` 根据受控类别生成 `safety_emergency`、`safety_medical`、`safety_eating_disorder`、`safety_special_population`、`safety_uncertain`，均为 422，保留原有安全提示。
- 隐私清理尚未完成使用专用 `privacy_cleanup_pending` / 503，保留原有重试删除任务的提示，不与模型不可用混淆。
- facts、events、planning、workflow 等抛出点已按领域参数、版本、幂等和执行状态逐项迁移。
- 安全分类、营养估算、回复表达和建议四处捕获已知模型/输出校验异常；新增测试确认这些路径不会把未知 TypeError 变成正常兜底。
- 前端 `ApiError.requestId` 与业务请求体 request_id 分离；计划取消依赖稳定错误码，新增测试使用完全不同的后端提示语验证行为。

错误日志默认只记录固定 code、HTTP 状态及服务端请求编号，不输出异常对象、异常链、请求体或供应商响应。局部降级另使用固定日志事件 `model_classifier_fallback`、`model_nutrition_fallback`、`model_reply_fallback` 和 `model_advice_fallback`。

删除错误的 preview 仅保留固定字段、已知统计键、非负整数和本地固定原因。标识允许 UUID，以及聊天事实使用的 `<UUID>:fact[:动作序号]`；无法通过安全格式校验的旧标识不回显在错误 preview 中，返回 preview=null，此时需重新查看删除预览，不能默认确认旧范围。
