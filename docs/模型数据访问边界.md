# 模型数据访问边界

模型负责提出计划，本地代码负责授权、取数和执行。首轮不提供历史记录；不存在通用数据库工具或由模型驱动的无限取数循环。

## 执行流程

1. `Parser.plan()` 只接收当前输入、当前时间和是否有选中记录，返回 `ProcessingPlan`。规划前不读取上轮引用，也不发送上轮结果数量。
2. `PlanHarness.approve_plan()` 校验任务原文、数据类型、窗口和指代。一次最多 4 个任务，可组合新增、查询、建议、长期信息；新增与纠错混合、多条纠错会先追问。
3. 程序绑定纠错目标，或构造建议数据视图。查询结果直接返回本地界面，不回传模型。候选选择只在本地界面展示，最多 5 条。
4. 本地构造器为确切内容创建本次调用授权；`ModelBoundary` 检查字段白名单和授权指纹，生成不可变、一次性请求。修改内容后必须重新通过本地授权。
5. `Parser.model_request()` 只接受已批准请求。服务器在打开网络连接前消耗授权并登记调用预算。没有授权、处于本地模式、超预算或包含额外字段时停止外发。

## 允许的数据视图

| 用途 | 外发内容 | 限制 |
| --- | --- | --- |
| 规划 | 当前输入、时间、操作状态 | 不含历史正文、记录 ID |
| 纠错 | 当前修改要求、绑定记录的必要字段 | 一条；ID、类型和版本由程序绑定；保留原日期 |
| 草稿补充 | 当前答案、当前草稿、待补字段 | 不附带其他记录；本地只合并待补字段 |
| 单餐指代 | 被绑定餐食的结构化字段 | 一餐，最多 10 个食物；不带当天其他餐食 |
| 单日饮食 | 用户指定日期的结构化餐食、汇总、完整性 | 默认今天；最多 10 餐、每餐 10 个食物 |
| 近期饮食 | 每日餐数、营养汇总、完整性 | 最多 7 天；更短要求按实际天数读取 |
| 体重趋势 | 日期、体重 | 最多 28 天；无饮食、周期、档案或聊天原文 |
| 分量建议 | 单日饮食、必要基础档案 | 档案只含年龄、身高、体重、目标体重、活动和营养情境 |
| 营养估算 | 当前食物、分量、已知及待估营养 | 不附带记录正文、历史或档案 |
| 回复润色 | 本地批准的要点、反馈类别、当前食物名 | 不附带反馈引文或历史上下文 |

饮食视图可携带最多 8 条已确认限制、5 条已确认偏好，以及营养目标和营养情境。所有字符串仍作为不可信数据处理，不能生成新的数据授权。裁剪和结构化可减少暴露范围，但不保证模型语义判断一定正确。

长期信息现以严格校验的结构化对象发送，包含类型、对象、取值、最短描述、执行策略、有效期、来源类别、自述严重程度与当前生命周期。来源人员、机构、文档、完整消息及修订记录不在投影中。限制超过条数预算、存在未决冲突或临时限制期限不足时停止普通生成；普通偏好可裁剪到 5 条。医疗信息仍受原安全入口限制。

规划响应可提出 `fact_draft`，其 schema 不含替代/覆盖 ID；它只是对本次输入的带原文证据草稿。本地程序决定是否确认、如何关联旧事实和是否需要核对，模型不能直接解除限制。原 `fact_text` 继续兼容。

当前未开放任意历史窗口。超出视图范围的建议申请会提示缩小范围或使用本地查询；不会悄悄发送更多数据。被允许的历史记录本身也可能包含敏感内容，因此纠错仍只发被明确选中或唯一指代的那一条。

## 指代与写入

优先使用当前选中记录；否则仅允许绑定同一会话上一轮唯一结果，并要求当前输入有明确指代。多个结果、不存在或已删除的记录不能自动猜测。模型返回的 `target` 只是建议，不能赋予权限。

上轮引用按需读取：先生成处理计划，只有纠错或建议任务需要解析当前原文中的历史指代、且没有选中记录时，才查询上轮回复的 `evidence_refs`。普通新增、本地查询、无历史指代的日期视图建议和意图澄清不读取这份引用清单；用户要求不读历史且采用 `none` 视图时，构造建议上下文也跳过指代取数。唯一性判断完全留在本地，不再通过 `previous_result_count` 告知规划模型。

纠错候选在追问前保存，恢复时只接受该次展示过的候选。绑定后不因会话新增消息而换到其他记录。保存前再次检查记录 ID 和版本；记录在补充期间变化则要求重新选择。模型纠错响应不含 ID 字段，也不能改变事件类型。其他写入仍经过现有字段校验、营养准备和幂等逻辑。

## 预算、恢复与本地模式

- 每次外发 payload 不超过 90,000 UTF-8 字节。
- 同一工作流累计最多 32 次外部调用、400,000 payload 字节，其中规划最多 4 次；失败调用也计数。
- `model_calls` 只保存流程 ID、用途、字节数和时间。重试和重启共用累计预算，不保存请求正文。
- checkpoint 保存的是流程状态，不是可复用外发授权；恢复后重新检查并创建本次授权。
- `local_only` 覆盖所有模型入口。模型流程可以在恢复时收紧为本地模式；已是本地模式的流程不能在恢复时自动升级。
- 本地解析能力有限；不认识的复杂表达需要澄清，缺失营养保持未知。

这是单用户本地原型中的数据最小化边界，不提供多用户身份认证或租户隔离。若后续引入多用户，必须在服务端的数据查询层另外加入所有者校验。

## 验证

### 输出 harness（local-output-v1）

`app/policy/output.py` 统一负责模型候选的输出授权和本地渲染。结构化输出只能保证格式；本地还检查候选是否属于这次上下文批准的选项。所有建议路径（包括新增记录后附带的建议）共用这层规则。

- 普通建议响应为 `{"point_ids":["review_portion"]}`。模型从本地提供的选项选择一到两项；未知、跨场景、重复标识以及附带 `answer/saved/targets` 等字段均拒绝。日期、记录餐数、热量合计、生效目标和差额按各自字段生成，完整性和来源说明是不可被模型删掉的必选内容。
- 反馈响应为 `{"segments":[{"point_id":"ack_salty","variant_id":"warm"}, ...]}`。模型只选本地批准的表达版本；要点不能删改、重排或加正文。自述和假设采用不同的本地表达，风险边界由本地追加。
- 外发 `options` 由同一策略生成，经过字段白名单、与本地选项比较及包含选项内容的单次授权指纹检查。修改上下文或选项后必须重新授权。
- 追问根据本地核验过的缺失字段及食物索引生成，模型 `question` 只保留为需要澄清的兼容信号。`clarification_fields` 可以单独申请追问；不能用另一食物的缺失状态追问当前食物已提供的字段。恢复中断时重新渲染选择和问句，忽略旧 `clarification_reply` 自由正文。
- 营养估算的数值仍需经过范围、一致性和来源校验；模型 `uncertainty` 不直接展示。新估算和复用旧估算都由本地生成未核验、分量/做法误差及示意误差带说明。用户值和演示值保留各自来源，建议中不会把演示固定值称为模型粗估。
- 保存回执仍由实际持久化后的本地记录生成，空记录列表不能生成成功回执。现有请求幂等、事务、版本与计划确认规则继续负责执行边界；本次未新增模型执行 SQL 或修改目标的能力。

当前普通建议限定在本地目录，不能提供任意新饮食方案。扩充时应增加经核对的目录条目、明确适用条件并补充测试，不能恢复为允许模型任意输出正文。已有完成会话的历史文本不做改写；待恢复的追问按新规则重新生成。

`test_output_policy.py` 覆盖状态伪造、数值角色互换、中文数字/日期绕过、额外字段、选择范围与顺序、追问夹带声明、旧 checkpoint 以及估算说明注入。`test_advice_generation.py`、`test_contextual_replies.py` 和 `test_harness.py` 通过模拟 HTTP 响应验证真实工作流的拦截和兜底。

`backend/tests/test_harness.py` 捕获模拟 HTTP 请求，检查无关历史和注入文本不外发、越界视图和伪造 ID 被拒绝、指代歧义追问、混合任务、查询结果留在本地、单餐范围、时间窗口、预算、授权内容变更及本地模式恢复。原有记录、营养、追问和幂等测试继续运行；测试不调用真实供应商。
