# 统一类型化工具接口开发方案

## 1. 背景与结论

当前 `Repository` 是 `health.db` 的总数据入口。文件已按记录、事实、工作流、计划、任务和数据来源拆分，但运行时仍组合成一个大对象，并被 API、工作流、后台任务和隐私删除模块直接使用。

Chat Graph v2 已将聊天写入集中到 `ChatOperations`，但命令的 `payload`、结果的 `records` 和多数 Repository 返回值仍是普通 `dict`；Chat 组件还持有完整 `Engine`，可以绕过约定访问 `engine.repo` 和 `.conn`。

本次目标不是增加一层 Pydantic 包装，而是建立真正的应用用例边界：

```text
模型 Plan（不可信）
        ↓ 本地校验、绑定原文和数据范围
服务端 Typed Command（可信结构，不携带自声明权限）
        ↓ 服务端注册表决定能力并重新授权
Handler + ExecutionContext（一次执行对应一个事务）
        ↓ 最小权限 facade
SQLite Repository
```

项目尚未上线，本地 `health.db` 和 checkpoint 可以清理，因此本次不兼容旧的命令字典和 checkpoint，只从新版本开始建立版本化契约。

## 2. 开发目标

- 每个工具只完成一种明确操作。
- 每个 Command、Result 和数据投影都有明确类型和大小限制。
- 模型不能直接获得 Command、capability、Repository 或数据库连接的控制权。
- 组件拿到的对象在运行时不存在无关写方法和 `.conn`。
- 写操作具有内容一致的幂等语义，而不只是“重复 ID 返回旧结果”。
- 一次 Handler 执行在一个 UnitOfWork 中原子提交。
- 单实体和多实体操作分别使用合适的并发条件。
- 回复、API 和模型上下文只获得各自需要的数据投影。
- 复用现有公共错误码体系，明确可重试的基础设施故障。

本次不更换 SQLite，也不重写全部 Repository。

## 3. 信任与权限边界

### 3.1 不可信 Plan

模型输出只表达意图、文本范围和候选字段。它不能提供或决定：

- `required_capability`；
- 用户或 tenant；
- `operation_id` 的最终作用域；
- 数据库主键、事务和授权结果；
- checkpoint 恢复后的继续执行权限。

### 3.2 服务端 Command

本地 Policy Compiler 校验模型 Plan，并生成带 `schema_version` 的判别联合命令。Command 不包含可由输入自行声明的 capability。

```python
class QueryEventsCommand(StrictCommandModel):
    schema_version: Literal[1] = 1
    kind: Literal['query_events'] = 'query_events'
    operation_id: str
    action_id: str
    start: str | None = None
    end: str | None = None
    event_kind: EventKind | None = None
    search: str | None = None


class CorrectEventCommand(StrictCommandModel):
    schema_version: Literal[1] = 1
    kind: Literal['correct_event'] = 'correct_event'
    operation_id: str
    action_id: str
    event_id: str
    expected_version: int
    event: PreparedEvent
```

命令类型与所需能力由服务端固定注册表映射：

```text
QueryEventsCommand   → query
SaveEventCommand     → record
CorrectEventCommand  → record
SaveFactCommand      → fact
```

### 3.3 ExecutionContext

ExecutionContext 由服务端在每次执行时重新构造，至少绑定：

- 当前认证用户；
- thread/workflow ID；
- workflow generation；
- operation ID；
- 当前安全策略版本和允许的数据范围。

checkpoint 只保存恢复所需的 Command 数据，不能保存一个可直接复用的授权。恢复时必须重新检查用户、workflow generation、安全上下文和命令类型。

### 3.4 运行时最小权限

`Protocol` 只用于静态检查，不能单独构成权限边界。实际注入必须是独立 facade/adapter 对象，而不是把完整 Repository 标注成较小接口。

```text
ChatInterpretation → EventReadFacade
ChatResponse       → ResponseProjectionFacade
ChatOperations     → ToolExecutor
ChatSafety         → SafetyRuntimeFacade
```

Chat 组件不再持有完整 `Engine`。只读 facade 在运行时不提供写方法和 `.conn`；ToolExecutor 是唯一获得聊天业务写能力的组件。

## 4. 幂等协议

幂等键作用域为：

```text
user_id + operation_kind + operation_id
```

写命令在执行前对规范化内容计算 `request_hash`。幂等记录至少保存：

```text
owner_id、kind、operation_id、request_hash、status、typed_result、created_at
```

处理规则：

- 相同作用域、相同 hash：返回第一次执行的相同 typed result。
- 相同作用域、不同 hash：返回 `request_payload_conflict`。
- 幂等记录和业务写入必须在同一事务提交。
- 执行失败不保存伪成功结果。
- 数据被隐私删除后保留不含健康内容的最小 tombstone，旧命令不能重新创建已删除数据。
- 幂等结果的保留周期不得短于对应业务数据和可恢复 checkpoint 的有效期。

现有请求层 fingerprint 和 `request_payload_conflict` 继续复用，不建立平行错误码。

## 5. 事务与并发协议

### 5.1 UnitOfWork

一次 Handler 执行对应一个顶层原子事务：

```text
BEGIN
  检查幂等记录
  检查版本或 read-set
  写业务数据
  写 revision / provenance
  写 operation receipt
  写 outbox
COMMIT
```

任何一步失败全部回滚。Repository 内部可以使用 savepoint，但最终提交权属于应用用例层。现有 `atomic(repo)` 和 `BudgetConnection` 的嵌套 savepoint 作为迁移基础。

模型调用、网络调用和真正的消息投递不得位于数据库事务内；事务只保存 outbox，提交后异步投递。

### 5.2 并发条件

不同操作采用不同条件：

- 单事件修改：`event_id + expected_version`。
- 多事实决策：目标版本加 `peer_versions` 或服务端 read-set token。
- 删除：preview ID、scope fingerprint 和目标版本。
- 计划激活：计划版本、偏好版本和依赖数据版本。
- checkpoint 恢复：workflow generation。

当操作会读取并影响 sibling facts 时，不能只检查主 fact 的版本。

## 6. 数据投影

Repository 内部记录不能作为所有调用方的统一返回值。健康事件至少区分：

- `StoredEvent`：基础设施内部完整记录；
- `EventSummary`：用户列表和聊天查询摘要；
- `EventDetail`：用户主动查看详情；
- `ModelEventContext`：最小化后允许发送给模型的内容；
- `SaveEventResult`：ID、version 和状态等写入回执。

长期事实采用相同原则。回复模块不能因为保存成功就获得完整数据库行；模型上下文默认不得包含不需要的 `raw_text`、内部版本或数据来源节点。

查询必须具有日期范围校验、limit 上限、稳定排序、搜索文本和总输入大小限制，并返回明确投影。

## 7. 类型与错误协议

### 7.1 类型模型

现有 `StrictModel` 实际只保证 `extra='forbid'`，不承诺禁止类型转换。本次区分：

- API Model：允许必要且经过测试的 JSON 日期、枚举转换；
- Closed Model：禁止未知字段；
- Strict Command Model：`extra='forbid', strict=True`，用于本地 Command、ExecutionContext 和 Result。

外部数据只能先进入 API/Plan 模型，再由本地代码显式转换成 Strict Command。

### 7.2 错误分类

复用 `app/common/errors.py`：

- 契约错误：结构、字段范围或 schema version 不合法；
- 业务拒绝：权限拒绝、版本冲突、事实冲突、幂等内容冲突；
- 基础设施故障：SQLite busy、磁盘错误、连接损坏等。

基础设施错误保留内部原因、`retryable` 和事务回滚状态，在 API/工作流边界映射为现有公共错误码。不得捕获所有 SQLite 异常并伪装成业务成功或普通参数错误。

## 8. checkpoint 与发布策略

Command、Result 和 checkpoint envelope 都携带 `schema_version`。未知版本必须在任何业务写入前安全终止。

由于当前没有线上用户，本次发布采用：

1. 清理本地旧 checkpoint 和测试业务库；
2. 新格式单写，不实现双读；
3. 不支持旧 `payload` 字典；
4. 增加未知版本不写入测试；
5. 从本版本开始，后续变更必须选择 upcaster、双读单写或显式终止策略。

## 9. 代码结构

```text
backend/app/tools/
  contracts.py       Command、Result、ExecutionContext 和投影
  facades.py         运行时最小权限读取 facade
  chat.py            注册表、授权和聊天 ToolExecutor

backend/app/infrastructure/repositories/
  ...                保留现有 SQLite 实现

backend/app/workflows/chat/
  ...                只依赖 facade、parser、policy 和 ToolExecutor
```

最终分层规则：

> 除 `backend/app/infrastructure/` 和明确批准的隐私、迁移、checkpoint 适配器外，生产业务代码禁止引用 `sqlite3`、数据库 `.conn` 或具体 SQLite Repository 类型。

该规则针对 `health.db` 业务 Repository；认证模块独立管理的 `accounts.db` 不属于本次工具改造范围，后续可单独迁入 infrastructure。

架构测试负责检查禁止 import、禁止 `.conn`、Chat 组件不持有 Engine，以及只读 facade 不暴露写能力。

## 10. 实施步骤

### 第一阶段：Chat 主链

1. 增加严格 Command、Result、ExecutionContext 和查询投影。
2. 删除 Command 中的 `required_capability` 和通用 `payload`。
3. 增加服务端固定能力映射和恢复时重新授权。
4. 增加只读 facade，使 Chat 组件不再持有 Engine。
5. ToolExecutor 使用 UnitOfWork 执行命令。
6. 为事件和事实写入增加 request hash 冲突检查。

### 第二阶段：API 与其他业务

1. API 改为调用业务 Handler，而不是自行组合 Repository 方法。
2. 为计划、事实决策和删除增加 read-set/scope 并发条件。
3. 将普通业务模块中的直接 `.conn` 访问迁回基础设施适配器。

### 第三阶段：底层维护边界

1. 将隐私删除、归档、任务和 checkpoint 标记为明确的高权限适配器。
2. 清理非批准目录的 `sqlite3` 和 `.conn` 引用。
3. 启用静态类型检查和完整 layer architecture test。

## 11. 验收标准

- Chat Command 不存在通用 `payload: dict` 和自声明 `required_capability`。
- Command、Result、ExecutionContext 带版本并能独立严格校验。
- Chat 组件不持有完整 Engine。
- 只读 facade 在运行时不存在写方法和 `.conn`。
- 相同 operation ID、相同内容稳定重放；不同内容返回 `request_payload_conflict`。
- 幂等记录与业务写入位于同一 UnitOfWork。
- 单实体版本、多事实 peer versions 和 workflow generation 按场景检查。
- 查询结果使用明确投影，不返回完整 Repository 行。
- 未知 command schema version 在写入前失败。
- `api/` 和 `workflows/chat/` 不直接访问 `.conn` 或 `sqlite3`。
- 新增契约、权限、幂等、事务回滚、投影和版本测试。
- 现有聊天、安全、追问恢复、删除、任务和并发测试全部通过。

## 12. 禁止的万能接口

不得建立以下形式的通用入口：

```python
tool.execute(name, payload_dict)
```

统一的是执行上下文、授权、幂等、事务、错误和审计规则；每种操作的输入、输出和可访问数据必须保持独立、明确。
