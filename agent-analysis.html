SAFETY ROUTING · 先判断能不能做，再决定怎么做

安全路由：先判断风险，再处理业务

“记录午饭”和“催吐后还想减肥”都在谈饮食，处理方式却不同。现在请求先经过本地规则和独立 LLM 分类，再由程序决定是否允许继续估算、给建议或生成计划。本节对照当前安全实现，前面的总览保留原业务链路快照。

为什么旧流程会漏掉身体不适？

问题来自《架构与安全 Review 建议》中的“医疗安全边界”检查。原来已有 medical_question()，但它只识别少量关键词，而且主要在回复阶段的部分分支使用。安全判断没有成为所有入口共同的前置检查。

“我头晕，晚饭吃多少？”

这句话同时包含身体不适和饮食咨询。旧正则没有“头晕”这个词，检查返回 False；代码便缺少一条强制停止普通建议的边界。低血糖、持续腹泻、催吐、未成年人和孕产期复杂问题，也存在类似的覆盖缺口。

原因一：关键词没命中，就缺少明确拦截 
# 修复前已有的检查 · 等价分行展示
def medical_question(text):
    return bool(re.search(
        r'血压|高血压|糖尿病|肾病|肾功能|心脏|胸痛|呼吸困难|'
        r'持续.*(?:痛|吐)|用药|吃药|药量|利尿|排盐|排毒',
        text
    ))

medical_question("我头晕，晚饭吃多少？")
# False：没有匹配到关键词

只增加几个词仍会留下隐晦表达，例如“吃完把东西弄出来”。因此增加独立 LLM 分类，负责理解这些语义。

原因二：检查位置靠后，部分业务已经能够执行
解析输入parse_initial→ 准备营养、保存prepare_nutrition / persist→ 生成回复respond

respond 的部分分支才调用医疗关键词检查；已保存记录的分支会组装营养说明与餐食评分，额外建议任务还有自己的执行路径。末尾的一句能力提示，不能阻止前面的估算、评分或附加建议。

混合请求尤其容易暴露这个问题：“记录午餐，另外我持续腹泻”；追问时突然补充不适，以及从计划入口提交目标，也需要共同的安全边界。

这次修复要达到的效果：先判断能否进入普通链路，命中风险就用本地固定策略结束；模型判断后、实际操作前和回复输出前继续检查。首次输入、追问及计划入口采用同一边界。

旧路径对照修复前提交 df50bb4。这里说明代码允许的漏判路径，不代表旧模型每次都会给出同样回答。medical_question() 仍保留为局部回复辅助，新的主安全入口已放到它之前。背景来源：架构与安全 Review 建议 · 3.5

不同输入会走哪条路？

“吃完就去卫生间，把刚吃进去的东西弄出来。”
① 本地没有命中明确词

没有直接出现“催吐”等词，交给独立分类模型理解，不在这里认定安全。

② 模型提出进食障碍风险

只返回 eating_disorder 等标签，并引用这句话中的原文；本地继续校验。

③ 使用固定求助引导

停止本次营养估算和减重建议，不把这句话继续交给普通饮食建议模型。

档案是什么？

用户明确提供的年龄、孕哺状态和医疗限制。它们是本地检查的依据；这一版没有另建长期“未解除风险”表，也不自动保存诊断。

模型说不清，怎么办？

超时、预算耗尽、非法结构或原文证据不匹配，都转为 uncertain。本地固定回复说明边界，已经保存的独立记录保留并说明。

没有模型，还能记录吗？

仅允许完整匹配离线白名单的记录、查询和明确食物偏好；不补演示营养、不评分、不附带建议。其他自由输入使用保守边界。

LLM 的“普通”不是医学安全证明。 本地规则与模型都有覆盖范围，输出检查也不是医学事实验证器。一次 16 条合成语料实测中，10 条风险均被拦截、6 条普通均放行，但有 2 条首选风险分支与标注不同；平均分类约 3.9 秒。这是小样本验证，不代表生产召回率或临床验证。

处理计划与数据边界

按当前源码核对：模型模式由 ProcessingPlan 选择类型化数据视图和显式日期，PlanHarness 只执行白名单、跨度、原文、指代与写入边界；计划校验失败时可用同一输入修正一次。每次模型请求仍经过同一个出口，这些调用都发生在 Graph 节点内部。

图上两处检查指的是同一个 ModelBoundary。PlanHarness 负责白名单审批、窗口上限与引用绑定；补丁、营养、表达和建议分别在业务节点构造资源，所有请求最后都走 Parser.request → approve → model_request → consume → HTTP。查询结果不送模型作二次总结；自然咨询正文会把同一受限 context 与草稿交给第二次独立审核。

场景、实际代码与数据范围放在一起看 · 按 2026-10-21 当前实现核对。

核心不是让模型自己遵守“少看数据”，而是程序先装好允许发送的数据，再审核模型提出的任务。下面是假设模型正确识别纠错意图时的代码推演，不读取真实健康记录，也不代表已经执行过一次模型请求。代码片段省略了无关分支。

用户输入

系统已保存，随后用户发现说错了：

本地数据边界

}

1一个数据集只回答一个问题

进程崩溃后怎样恢复？

结合当前代码的通俗讲解 · 2026-10-28 · 代码为关键逻辑摘录，省略部分参数与校验。

Agent 恢复执行靠数据库里的“流程存档”，不是让模型回忆自己执行到了哪。整条链路分成三件事：存进度、找回进度、重复执行时避免重复写数据。

1. 进度存在哪里？

Engine 启动时打开专门保存流程进度的数据库。GuardedSqliteSaver 是项目对 LangGraph SqliteSaver 的封装。

self.checkpointer = GuardedSqliteSaver(self.cp_conn, self)

# chat_flow.py：构建流程时接上存档系统
return graph.compile(checkpointer=self.checkpointer)

可以把它理解成游戏的“存档系统”：流程状态和执行进度持久化到磁盘，进程退出后存档还在。

2. 重启后怎样找到原任务？

关键是 thread_id，相当于这一次工作流的“存档编号”。runtime.py 先通过 request_id 找原来的工作流：

4. 记录已写入，进度未保存怎么办？

如果重新插入，用户只跑了一次步，数据库里就可能出现两条记录。因此 chat_flow.py 写入时使用固定的操作编号：

def save_events(self, drafts, op_key, ...):
    with self.lock, self.conn:
        old = self.conn.execute(
            'SELECT result FROM operations WHERE key=?', (op_key,)
        ).fetchone()
        if old:
            return json.loads(old['result'])
        # 未执行过，才继续写入

这就是业务幂等：同一项保存操作重复调用，返回原来的结果，避免重复产生业务记录。saved_indexes 能帮助流程跳过已保存事件，但遇到“业务已提交、checkpoint 未更新”的缝隙，还需要数据库里的操作记录兜底。

5. 回答已消费后再次崩溃怎么办？

runtime.py 会查看当前存档里，那个中断是否还存在：

invocation = (
    Command(resume=answer)
    if payload['interrupt_id'] in interrupt_ids
    else None
)
  • 还在等这个回答：用 Command(resume=answer) 提交回答。
  • 回答已被消费，且存在匹配的恢复尝试：用 None 继续流程，避免再次提交同一个回答。没有匹配尝试或校验不通过时，不会直接放行。

执行前会保存 resume_attempts，执行成功后保存结果回执。启动时把遗留的 executing 尝试标为可重试的失败状态。重试如果已有成功回执，就直接返回原结果。

记住这条链路：thread_id 找存档，checkpoint 决定从哪里继续，interrupt_id 对准待回答的问题，request_id 和业务操作键防止重试造成重复执行效果。

边界：两个数据库的提交不是同一个原子事务，所以需要业务幂等。重启会重新打开存档，但普通交互流程需要原请求重试或恢复调用来触发继续，并不是启动后自动把所有流程都跑起来。

共享引擎与锁的边界

多个请求可以共用一个 Engine。即使只有一个用户，也可能一边等待聊天回复，一边点击计划确认或删除记录。原来整个 Graph 都拿着全局锁，一个慢模型会让其他需要这把锁的操作排队。

本地处理：加锁校验请求、读取数据、保存进度
→
HTTP 等待：释放全局锁不同对话、计划确认、删除和调度可进入
→
返回：重新加锁并检查删除 / 取消优先；上下文已变化则停止旧结果

现在 Graph 调用本身不持有全局锁；本地步骤和进度存档的读写短暂持锁。model_io() 在同一节点线程等待模型时释放全局锁，模型返回后重新拿锁，并检查期间是否发生删除、取消或相关数据变化。工作流自己的锁仍然保留，所以同一流程、同一对话依然按顺序执行，不同对话可以并行。

对应代码：concurrency.py · model_io() / serialized_execution()。timeout=45 是 HTTPX 的网络阶段超时，不是整个 Graph 总耗时最多 45 秒。

第五步：确认与取消争用同一操作权

可以把工作流锁理解为“这份计划当前由谁操作”。确认进入 serialized_execution() 后，拿着 ('workflow', thread_id) 对应的锁，直到处理结果登记结束。取消同一份计划，也必须尝试拿这把锁。

    if not acquired:
        raise WorkflowConflict('计划正在确认，请稍后刷新状态，尚未取消。')
    with self.lock:
        self.repo.cancel_workflow(thread_id)
        self.checkpointer.delete_thread(thread_id)

blocking=False 就是：拿不到锁就立即结束这次取消，不排队等待，也不会在确认结束后自动再取消。这套机制没有“点击取消就中断正在执行的确认”的能力。

③ 确认继续如果成功，计划生效并释放锁

第六步：相关登记一起提交

假如程序只记下“流程成功”，还没记下“请求 A 已成功”就崩溃，重启后这些登记就对不上了。因此 finish_resume() 把下面四项放进同一个数据库事务。

# Repository · finish_resume()（结构示意，省略 SQL 参数）
with self.lock, self.conn:
    # 1. 更新 workflow 状态和结果
    # 2. 保存 receipts：请求 A 已成功，以及上次的结果
    # 3. 标记 resume_attempts：这次答案处理已完成
    # 4. 保存助手回复

self.lock 让这些受保护的数据库操作按顺序进行；self.conn 管理数据库事务，成功一起提交，中途异常则回滚这一组修改。计划取消也将“计划拒绝”和“流程取消”一起提交。

如果只是成功回复在网络上丢了，原请求重试时，_resume_receipt() 找到成功凭据后直接返回上次结果，不再执行 Graph。但这个事务只覆盖最后的登记，不会自动撤销前面节点已经保存的健康记录，也不包含另一个数据库里的 Graph 存档。

对应代码：Repository · finish_resume() / cancel_workflow()；成功结果复用：runtime.py · _resume_receipt()。

后台任务可靠性 · 对应 Review 7.1 · A 期代码与验证核对：2026-10-27

后台任务：不重复执行，中断后可恢复

可以把 scheduler 理解成“定时看待办清单的人”。现在它只负责把到期任务记下来，后台执行器再逐个领单。待办、领取记录和结果都写进数据库，服务重启后可以查清：哪些已经做完，哪些需要继续。

修改前：标了“正在做”，别人仍能再领

旧 start_job() 没有排除 running。A 开始生成周报时，B 仍可能领到同一任务；A 写“已完成”之后，B 的失败回执还能把任务改回“待执行”。已有的通知去重只能减少重复通知，管不住这段执行过程。

修改后：领单要拿凭证，交结果也要核对凭证

任务只能通过一次不可被其他领取插入的数据库操作取得执行权。执行者拿到一张有有效期的“领单凭证”；续期、保存结果和结束任务都要核对。凭证失效后，迟到的成功或失败回执都会被拦住。

① 到点登记plan_jobs() 扫描日报、周报和提醒；这里只排待办，不执行 Graph。
② 待办落库scheduled_jobs 保存任务。同一业务编号、同一代次只登记一份，例如当天午餐的餐前提醒。
③ 领单执行run_one() 先申请运行名额，再领取一条任务；默认后台一次做一件。
④ 提交或恢复核对凭证后记为完成。中断后租约过期，按窗口与次数决定重试、跳过或失败。

代码中的四个关键点

1 · 单个引擎为什么仍需加锁？

Engine.__init__() 在打开数据库之前，先取得 DataOwner 的操作系统文件锁。第二个服务如果使用同一个数据目录，会在开库前退出。这样避免工作流锁、进度存档和删除恢复分散在两个 Engine 中，各管各的。

2 · 领取凭证为什么会过期？

claim_job() 在短事务中领取任务，并生成 lease_token。默认租约 90 秒，独立连接每 20 秒报告一次“我还在执行”并续期。执行者崩溃后心跳停止，recover_jobs() 才能回收；旧凭证不能续期复活，也不能覆盖接手后的结果。

3 · 重试会生成重复报告吗？

同一任务重试继续使用原 request_id 和已保存进度，不因为“第二次尝试”就换一个业务编号。报告日期、计划起始日期也固定下来，跨午夜恢复不会自动挪到另一天。默认最多尝试 3 次；过期提醒直接跳过，需要用户确认的计划仍等用户确认。

删除预览会计算关联任务和后续事件。确认删除时撤销旧凭证、清掉路由副本，并提升业务 generation，相当于宣布“这一代任务作废”。业务写入和 checkpoint 提交前都检查执行权；纯本地模式也跟着任务和后续事件保存，恢复时不能自动放宽。

周报完成后重启，计划怎样继续？

这里用 outbox，也就是“后续待办箱”：周报收尾时，把周报完成登记和“接下来需要生成计划”一起保存。另一轮再读取待办箱，创建计划任务。计划失败只处理自己的失败，不会把已经完成的周报改回待执行。

周报结果已落库 → 同一事务保存「周报完成 + 站内通知（开关允许时）+ 生成计划的待办」→ 消费待办并创建唯一计划任务。

最小权限运行：限制权限、数量和时间

模型可以提出处理计划，程序仍要决定这次请求能读写哪里、占多少资源、执行多久。这次修复同时补上运行环境的权限限制和请求执行中的资源检查，保留已有的数据授权、安全路由和幂等恢复机制。

为什么还要限制运行环境？

《架构与安全 Review 建议》6.3 指出：原启动脚本直接用当前登录账户运行 Python，仓库没有独立低权限账户、只读文件系统或默认拒绝的网络出口。即使正常代码只往 data 写数据库，也没有操作系统规则禁止进程访问启动账户有权限访问的其他位置。

此外，原来的“聊天最多 4000 字符”是在 JSON 读入后校验；模型 HTTP 的超时也不等于整轮任务的总期限。超大正文、持续缓慢返回的模型响应和大量同时到来的请求，都需要更早、更完整的限制。

原来已有：限制模型能申请什么

ModelBoundary 检查用途、数据视图和一次性授权，模型不能任意选记录、SQL 或字段；但这层检查不能收缩 Python 进程的系统权限。

这次补上：限制进程和请求能消耗什么

容器收缩文件、身份和网络范围；应用在接收正文、进入工作流、调用模型及提交数据库时检查大小、数量和时间。

这是运行隔离与资源控制缺口，不代表已经发现“提示注入直接执行 Shell”的利用路径。当前工程没有向模型提供 Shell 工具；非 root 和只读配置也不能被解释成“操作系统禁止所有子进程”。

示例：只删体重，其他记录怎么办？

E2 · 跑步事件保留独立内容

聊天与结果副本只处理相关副本

M1 包含体重，需要清理；其他能证明独立的消息保留。

W2 · 独立待补充流程继续使用

① 原因：为什么原来会全部清理？

体重不只存在于 events。助手可能回复“已记录65公斤”，workflow.result、receipt 和 checkpoint 也可能保存这句话。只删事件行，其他位置仍可能展示或恢复它。原实现因此选择“所有可能藏副本的上下文一起清理”。

怎样查找依赖并避免重复？ 
# repositories/provenance.py · 节选
found, frontier = set(roots), set(roots)

        following.update(row[0] for row in self.conn.execute(

为什么删除也要处理进度存档？

这里有三样不同的东西：业务数据、流程存档、删除任务记录。checkpoint 就是“流程存档”，类似游戏存档：程序中断后，可以知道之前做到哪里、接下来做什么。

今天体重65公斤，请帮我分析一下。
① 保存体重记录 E1
        ↓
② 读取最近的体重变化
        ↓
③ 请求模型生成分析
        ↓
④ 保存分析结果
        ↓
⑤ 给用户发送通知

这整个任务叫一个 workflow（流程），这里编号为 W1。checkpoint 保存它执行过程中的状态，例如：

# 示意结构，方便理解，不是工程中的完整存储格式
checkpoint = {
    "thread_id": "W1",
    "next_step": "保存分析结果",
    "state": {
        "event_id": "E1",
        "weight": 65,
        "model_result": "最近体重有所下降……"
    }
}

checkpoint 不只记录“执行到了第几步”，也可能保存任务用过的数据、对话和模型结果。所以业务表里的 E1 删掉了，流程存档里可能还留着“65公斤”和相关分析；仅删除业务记录，隐私副本可能仍然存在。

对象可以理解成什么例子
业务数据用户正式保存的记录和结果E1：体重65公斤，以及相关聊天、分析等。
checkpoint任务的执行存档W1 做到哪一步、用过的数据和中间结果。
删除任务记录删除操作的工单清理哪些对象、哪些流程，以及清理到哪个阶段。

W2 是什么？它只是另一次任务的编号，例如根据 E2 跑步记录生成运动建议、正在等待用户补充信息的流程。只要没有使用 E1，且来源可以证明独立，删除 E1 时就应该保留 W2 的消息、等待状态和存档。

⑤ 防止写回：只让相关流程失效

为什么删除后旧任务还能写回？ 
W1 读取 E1：体重65公斤
        ↓
W1 把数据发给模型，等待返回
        ↓
用户删除 E1，系统也删除 W1 的 checkpoint
        ↓
模型返回分析结果
        ↓
如果没有额外检查，旧 W1 又把分析结果保存回数据库！

删除存档，不等于停止正在运行的程序。程序内存里可能还拿着旧数据，模型请求也可能还没有结束。就像你销毁了桌上的文件，但同事之前已经拿走一份，稍后又把处理结果放回桌上。

所以还要检查：这次任务是否仍然有资格继续写入？原来所有任务共用一个全局版本号，删除时这个号码一变，W1 和无关的 W2 都会失效；全量清理 checkpoint 又把两者的存档一起删除。

现在每个流程单独保存一个 generation，可以理解成执行凭证的版本号。假设 W1 和 W2 启动时都拿到自己的第1版凭证：

流程使用的数据删除 E1 前删除 E1 后
W1：体重分析E1数据库版本1，运行任务持有版本1。数据库变成版本2，旧任务仍拿着版本1，拒绝继续写入。
W2：独立跑步任务E2，没有使用 E1数据库版本1，运行任务持有版本1。版本仍为1，通过其他必要检查后可以继续。
# 白话伪代码；下方对照卡片展示工程中的写法
if 数据库里的流程版本 != 任务启动时的版本:
    拒绝旧任务继续写入

数字从0还是从1开始不影响原理；关键是新旧版本不相等。清理相关存档，解决已经保存的副本；改变相关流程的版本，拦住仍在运行的旧任务。这不一定能立即取消外部模型请求，但可以阻止旧结果再次落库。

删除中途退出后怎样继续？

数据分在两个数据库里：health.db 保存 E1 和相关业务内容，checkpoints.db 保存 W1 的执行存档。因此，完整删除需要处理两边。

修改前可能发生：
① 删除健康数据库中的 E1 → 成功
② 删除 checkpoint       → 失败，例如数据库暂时被占用
③ 程序退出

结果：E1 已经没了，但流程存档里的副本还在。

原来的顺序调用，没有留下可供程序恢复的持久记录，告诉下次启动的服务：“上次还剩 checkpoint 没清完”。异常日志供人排查；删除工单供程序自动接着做。

现在先在数据库里保存一张工单，再开始分阶段清理：

# 示意结构，不是工程中的完整工单字段
deletion_job = {
    "id": "D1",
    "target": "E1",
    "affected_threads": ["W1"],
    "state": "business_pending"
}
工单状态通俗含义
business_pending业务数据还需要清理。
checkpoint_pending业务清理已完成，还需要清理流程存档和存储。
completed要求的清理全部完成。

代码中 with repo.conn: 包住的重点是：业务清理与工单更新为 checkpoint_pending，在健康数据库的同一个事务里完成。它们一起提交，或者一起回滚，避免“业务清完了，却没记下下一步”。

工单 D1：business_pending
        ↓ 业务清理与阶段更新，一起提交
工单 D1：checkpoint_pending
        ↓ 假设这时清理存档失败，程序退出
工单仍保存在数据库，状态没有丢
        ↓ 用户重试，或者服务重启恢复
读取 D1，继续处理剩下的 checkpoint 和存储清理
        ↓ 全部成功
工单 D1：completed

中途失败时返回 pending、deleted=False，意思是整个删除任务尚未完成，并不表示前面的业务删除一定没有发生。这两个数据库仍然不是一个事务；改进在于跨库操作中断后，系统有可靠的记录继续完成，不会假报成功或忘掉剩余工作。
