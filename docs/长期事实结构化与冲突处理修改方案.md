# 长期事实结构化与冲突处理修改方案

> 当前客户端为微信小程序，事实管理与类型位于 `miniprogram/native/pages/facts` 和 `miniprogram/native/contracts.d.ts`。本文原 Web 路径为历史背景，详见 [微信小程序开发方案](微信小程序开发方案.md)。

日期：2026-10-26  
状态：已实施并通过回归验证；当前实现说明见《四层记忆实现说明》的结构化长期事实部分

## 1. 修改目标与现状

沿用现有 `facts`、`fact_details`、`fact_revisions` 和 provenance，补全“原文提取 → 结构化事实 → 时间与冲突解析 → 建议/计划使用”的完整链路。

当前已经具备事实分类、起止日期、版本、来源消息、替代、冲突确认和到期处理。本次重点是修复覆盖缺口，而不是重新设计全部记忆系统。

已确认的缺口：

| 环节 | 当前行为 | 目标行为 |
| --- | --- | --- |
| 对象归一化 | “不喜欢吃燕麦”得到对象“吃燕麦”，无法匹配“燕麦” | 两种表达得到同一对象；无法可靠匹配时保持待核对 |
| 临时表达 | “暂时不吃燕麦”退回无期限的自由文本 | 明确记录为临时且期限未知，按需追问 |
| 临时冲突确认 | 选择临时事实会将原偏好标成永久被替代 | 仅在临时有效期覆盖，到期恢复原偏好 |
| 专业建议 | 有来源类别和日期，但聊天通常不提取 | 提取用户明确提供的期限与来源，保留证据 |
| 风险处理 | 有医疗安全路由，缺少事实级语义 | 区分普通偏好、需避免事项、需专业评估事项 |
| 下游使用 | 建议和计划主要读取 `content` 文本，且有固定条数截断 | 使用统一的结构化有效事实视图，保留日期、来源和约束语义 |

本次不改变营养目标算法，不生成诊断或治疗方案，也不因补充风险字段而放宽现有医疗安全入口。

## 2. 数据结构：保留原文，补充可判断的字段

### 2.1 存储与兼容

- `facts.content` 继续保存用户原话，作为展示、证据和兼容字段。
- `fact_details.data` 升级至 `schema_version=2`，保存以下结构化信息。
- `fact_revisions` 保留每次变化；现有 `version`、`expected_version` 和操作去重继续使用。
- 暂不将所有 JSON 字段拆成数据库列；后续如有明确查询性能瓶颈，再添加索引字段。

### 2.2 字段约定

| 字段 | 方案 |
| --- | --- |
| `type` | 保留现有类型，增加 `health_condition`，表示用户自述疾病或健康状况 |
| `subject` | 用户提供的对象名称，用于展示 |
| `subject_kind` | `food / condition / nutrient / activity / other`，避免不同对象域误合并 |
| `subject_key` | 本地归一化后的稳定键，用于同一对象比较 |
| `value` | 按类型校验：偏好限定枚举；限制、过敏、健康状况和专业建议分别定义允许的结构和状态，不能共用任意字符串解释 |
| `restriction_reason` | `preference / allergy / health_condition / professional_advice / other / unknown`；无法判断时保留未知 |
| `time_scope` | `persistent / bounded / temporary_unknown / unknown`，区分长期、明确期限、临时但期限不明和未知 |
| `valid_from / valid_until` | 事实适用日期，按应用时区解释，结束日期当天仍适用 |
| `source_kind` | 保留用户明确陈述、用户转述专业建议、历史来源和待核对提取的区分 |
| `source_details` | 可选的专业人员称呼、机构、建议作出日期、文档描述；仅保存用户提供的内容 |
| `assertion` | `affirmed / denied / uncertain / hypothetical`，区分明确陈述、否认、不确定和假设 |
| `evidence` | 结构化字段与原文片段、来源消息的对应关系；包含时间和来源描述的证据 |
| `supersedes` | 延续永久更新关系，用于明确替代旧事实 |
| `overrides` | 临时覆盖的旧偏好 ID 列表，覆盖范围由新事实有效期限定 |
| `reported_severity` | 可选的用户自述严重程度，缺失时为 `unknown`，不得根据类型自动填写 |

专业建议中的“建议作出日期”与 `created_at`、`valid_from` 分开。保存时间不能冒充医生建议时间，用户确认也不能变成独立医疗核验。

`confirmation` 继续表达用户是否确认这条陈述；`lifecycle` 表达事实生命周期。某一天是否适用、是否被临时覆盖、是否存在冲突，由有效事实解析器输出，避免把暂时状态永久写入原事实。

### 2.3 风险语义

增加由本地策略派生、客户端不可任意写入的 `enforcement`：

| 值 | 含义 | 处理 |
| --- | --- | --- |
| `soft` | 普通喜好、可接受程度 | 可以按明确更新或临时覆盖规则处理 |
| `avoid` | 明确需避免的事项 | 纳入限制，不被“现在喜欢/可以接受”自动解除 |
| `clinical_review` | 过敏、健康状况、转述专业建议等需要专业评估的信息 | 沿用现有医疗安全限制，冲突和到期待核对期间保留保护 |
| `unknown` | 事实含义、原因或适用范围不足 | 标记待核对；涉及相关食物或计划决策时按现有不确定性入口处理 |

这是产品执行策略，不是临床危险程度排名。`reported_severity=unknown` 不代表低风险，模型置信度也不能作为解除限制的依据。

“我不吃燕麦”未说明原因时，不自动当成可被新喜好覆盖的普通偏好；保留避免信号，必要时核对原因。

## 3. 写入与提取流程

### 3.1 本地解析优先覆盖清晰表达

改造 `health/facts.py`：

1. 分开解析主语、谓词、对象和时间修饰；覆盖“不喜欢吃”“现在能接受”“这周不吃”等明确表达。
2. 以谓词边界提取对象，修复“吃燕麦”误当对象的问题；不通过全局删除“吃”字修复。
3. 使用受控、可测试的别名表；只合并明确同义名称。食材与混合食品不能因包含相同词语就自动合并。
4. “今天”“本周”使用现有时钟计算；“未来两周”锚定首次输入日期，重试不移动期限。
5. “这两周”可能指过去或未来，“暂时”“最近”缺少明确边界，记录原文与期限不确定性，不猜结束日期。

### 3.2 模型输出结构化草稿，程序决定能否生效

在 `ExtractionResult` 和 `PlannedAction` 增加有类型约束的事实草稿，保留 `fact_text` 兼容旧格式。模型仅可提出本次原文支持的字段，不得指定任意旧事实 ID、直接决定替代、填写权威核验状态。

本地程序依次校验：

- 对象是否为用户本人，是否为明确陈述；朋友、家人、假设和疑问不能成为用户有效事实。
- 对象、取值、时间和来源是否有对应原文证据。
- 原文与结构化字段是否冲突；有冲突则保存草稿，不能采用模型字段覆盖原文含义。
- 适用期和类型是否完整；临时且期限不明的信息进入待核对，不转成永久偏好。
- 是否命中安全入口；结构化提取不能绕过已有安全路由。

现有医疗输入会在事实持久化前进入安全回复。本期不在该入口后自动新增医疗事实；用户可在管理界面明确录入。医疗文本的提取与日期解析支持复用同一校验器，但聊天自动保存医疗信息留作独立变更。

### 3.3 管理界面与接口校验一致

手动录入也必须通过相同的字段校验、对象归一化、期限和冲突规则。用户通过表单提交不等于可以跳过风险判断。

输入“暂时不吃燕麦”时，界面显示“临时限制，期限待补充”，允许补充日期或撤回；不默认填写永久。

## 4. 时间与冲突规则

新增统一的有效事实解析器，例如 `resolve_facts(reference_date, purpose, subject_keys=None)`。建议、安全判断和计划安排使用这个入口；管理列表仍可查看全部事实。

解析顺序：确认与陈述状态 → 适用日期 → 永久替代 → 临时覆盖 → 同对象冲突 → 风险策略。

| 场景 | 处理规则 |
| --- | --- |
| 相同对象、相同含义、相同期限和来源 | 去重，绑定新操作凭据；保留新增来源证据，不制造无意义的偏好更新 |
| 普通长期偏好明确更新 | 新事实永久替代旧偏好，保留历史及替代关系 |
| 临时普通偏好与长期偏好不同 | 建立有期限的覆盖，保留长期偏好；到期后原偏好自动恢复 |
| 临时偏好没有结束日期 | 不建立无限期覆盖，保留待核对状态 |
| 两条时间不重叠的事实 | 不视为同时冲突 |
| 两条同时适用且无法确定关系的事实 | 输出冲突组，要求明确选择；不只按最新写入时间决定 |
| 新偏好与过敏、健康限制、专业建议冲突 | 普通偏好不能替代或覆盖保护性信息；保留安全入口 |
| 保护性信息到期 | 标记待核对，继续保护；不自动推断限制解除 |
| “不再过敏”“已经好了”等解除陈述 | 作为需要明确解决的更新，不能通过普通偏好覆盖路径生效 |
| 未来生效的更新 | 生效前不影响当前事实；生效后按其目标日期解析 |

临时覆盖至少记录新旧事实关系和有效期。撤回覆盖后，原偏好恢复；确认临时例外不再把原偏好写成 `superseded`。如果用户要永久改变偏好，应单独选择“设为长期更新”。

冲突应按对象及时间交集计算。现有 `confirmation=conflict` 的数据在读取时兼容，但新解析逻辑不能仅依赖该全局字段，否则某一天的冲突会错误影响其他日期。

跨类型检查主要防止保护性信息被解除，不把同一食物的“过敏”和“不喜欢”当成只能二选一的矛盾。疾病与食物限制之间的联系只使用用户明确提供的关联，不推断疾病对应忌口。

覆盖与替代操作在单个事务内校验涉及事实的版本，拒绝循环、自引用、已失效目标以及越过保护规则的关联。重放旧请求不能恢复已被更新的偏好。

## 5. 建议、安全与计划统一消费

### 5.1 结构化上下文

将建议上下文中的 `constraints`、`preferences` 从字符串数组改为受控结构数组。每项仅发送生成所需字段：类型、对象、规范取值、执行策略、适用期、来源类别、是否待核对，以及最短必要描述。

来源消息、专业人员姓名、机构、文档原文和完整修订记录保留在本地。它们可供用户核对，但不默认发给模型。事实 ID 和版本在本地记录真实依赖，不必对模型暴露。

同步修改 `modeling/payloads.py` 白名单、类型校验和长度限制，以及 `modeling/parser.py` 的建议提示词。不能只改构建上下文的一端。

普通偏好可按相关性和条数预算选取；保护性信息不能因为 `[-8:]` 或 `[-3:]` 被静默遗漏。若相关限制超过发送预算，先由本地限制生成能力并提示补充或核对，不让模型在不完整限制下继续生成。

### 5.2 安全入口

`local_safety()` 和计划资格检查消费相同解析结果，同时保留现有文本风险兜底。候选信息不得作为已经确认的健康事实用于普通建议；本次原文中的安全信号仍走原有安全检查。

风险策略版本纳入指纹。保护性信息新增、更新、撤回、到期待核对或冲突解决后，旧安全判断和相关草案必须重新检查。

### 5.3 未来计划按天解析

`health/planning.py` 目前把当前事实拼进一周每一天，需要改为针对每个安排日期读取有效事实。例如仅周一有效的临时偏好，不能影响周二至周日。

计划确认前重新校验相关事实版本、有效期及解析策略版本。跨越事实生效/到期边界时，即使没有新写入，也不能复用过时结论。历史建议保留当时使用的事实快照与版本，不用当前偏好重写过去结果。

## 6. 管理界面与历史数据

### 6.1 界面

扩展 `MemoryPanels.tsx`：

- 显示事实类型、来源、适用期、临时/长期状态、待核对原因及执行策略。
- 专业建议提供可选来源详情和“建议作出日期”，明确标注“用户转述”。
- 冲突面板展示冲突原文、日期交集及处理结果；普通偏好提供“仅在该期限覆盖”“永久更新”“保留待核对”。
- 涉及保护性信息时，展示明确的编辑或撤回入口，普通偏好选择不能间接解除限制。
- 展示临时覆盖到期后会恢复哪条偏好，避免用户误以为旧偏好已删除。
- 修改、确认和冲突解决失败时保留表单，提示刷新；继续使用版本检查。

### 6.2 迁移与回退

升级数据库版本至 7，迁移可重复执行且以事务提交；先在隔离旧库副本验证，再应用到实际数据库。

- v1 结构化事实补充安全默认值，不改变原内容、来源和既有版本历史。
- 历史 `legacy_text` 保持原样，不在启动或读取时批量调用模型，也不批量确认疾病、过敏和期限。
- 对旧 `food_preference/avoid` 保留避免语义，原因未知时不自动降为普通喜好。
- 既有 `superseded` 关系保留；无法证明曾是临时覆盖的旧操作不自动反转，可由用户修正。
- 新接口提供 v2 结构化响应；旧请求缺少新字段时按未知处理。涉及 `constraints` 结构变化的内部模型接口与前后端在同一版本发布。
- 旧 checkpoint 以适配器读取旧事实草稿并重新校验；无法适配时明确要求重提，不重放旧写入。
- 不支持直接用旧版程序写入已经升级的数据；回退采用迁移前备份，并明确回退会丢失备份后的新写入，不能静默覆盖。

扩展来源和覆盖关系后，继续使用现有 provenance 管理依赖、版本与来源副本。事实删除必须覆盖新增字段、全部修订、覆盖引用、导出和派生结果，避免新字段绕过已有精准删除逻辑。删除临时覆盖可恢复原偏好；删除被覆盖事实要清理悬空引用，不能重建已删除内容。

## 7. 实施顺序与文件范围

| 步骤 | 主要文件 | 交付结果 |
| --- | --- | --- |
| 1. 契约和迁移 | `contracts/facts.py`、`infrastructure/database.py`、`repositories/facts.py` | v2 字段、旧数据兼容、版本和原子写入 |
| 2. 提取与归一化 | `health/facts.py`、`contracts/workflows.py`、`modeling/parser.py`、`parsing/demo.py` | 修复对象识别、补充期限与来源证据校验 |
| 3. 有效事实解析 | 新增 `health/fact_resolution.py`，调整 `repositories/facts.py` | 永久替代、临时覆盖、按日期冲突与恢复 |
| 4. 工作流接入 | `workflows/chat_flow.py`、`chat_response.py`、事实草稿校验与 API | 聊天和手动录入采用相同规则，补全待核对反馈 |
| 5. 消费链路 | `health/advice.py`、`planning.py`、`safety.py`、`workflows/safety.py`、`modeling/payloads.py` | 结构化上下文、限制预算、按日计划与重新校验 |
| 6. 界面和数据生命周期 | `api/profile.py`、`frontend/src/types.ts`、`MemoryPanels.tsx`、provenance、删除及导出模块 | 可解释的冲突操作、完整来源与删除覆盖 |
| 7. 验收和文档 | 后端事实/安全/计划/隐私测试、前端面板测试及记忆文档 | 自动化证据与迁移说明 |

步骤 1–3 先在仓储与解析层完成验证；步骤 4–6 完成后作为完整变更接入产品，避免出现“保存支持新字段，实际建议仍只用旧文本”的中间状态。

## 8. 验收场景

| 编号 | 输入或操作 | 必须满足 |
| --- | --- | --- |
| A01 | “我不喜欢燕麦”→“现在可以接受燕麦” | 当前只采用新偏好，旧版可追溯 |
| A02 | “我不喜欢吃燕麦”→“我现在可以接受燕麦” | 两条归一化到同一对象，不同时生效 |
| A03 | 原来不喜欢燕麦，今天可以接受；确认临时覆盖 | 今天采用临时偏好，明天恢复原偏好 |
| A04 | 在临时覆盖结束前撤回它 | 原偏好立即恢复，保留操作历史 |
| A05 | “我暂时不吃燕麦” | 显示临时且期限未知，不自动成为永久事实 |
| A06 | 周一录入“未来两周可以接受燕麦”，第二天重试同一请求 | 起止日期不漂移，不重复写入 |
| A07 | 两条适用时间不重叠的偏好 | 不产生同时冲突；计划按对应日期采用 |
| A08 | 同一对象同时有效的未决冲突 | 普通建议不任选一条；保留保护性信息 |
| A09 | 已记录花生过敏，再说“现在喜欢花生” | 不能解除过敏或绕过现有安全入口 |
| A10 | 手动录入转述建议、来源和明确期限 | 分开保存建议日期、适用期和录入时间，展示为用户转述 |
| A11 | “医生可能建议我少吃”或“朋友对花生过敏” | 不成为用户已确认的专业建议或过敏事实 |
| A12 | 保护性信息到期、严重程度未知 | 到期待核对，不能自动当作低风险或已经解除 |
| A13 | 原文写“不吃”，表单或模型字段写“可以接受” | 拒绝矛盾写入或进入待核对，不能凭字段绕过原文 |
