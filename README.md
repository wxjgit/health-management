# 轻记 · 个人减脂 Agent

前端已统一为微信小程序，Web 前端已废弃。工程与导入方式见 [miniprogram](miniprogram/README.md)，功能映射与验收见 [微信小程序开发方案](docs/微信小程序开发方案.md)。

一个支持微信登录与账号独立数据存储的小程序，连接可本地运行的 Python API 服务，必须登录后使用。用自然语言记录饮食、体重、睡眠、运动和生理周期，数据保存在 SQLite 中；LangGraph 负责解析、关键追问、纠错、历史检索、计划确认和复盘流程。

## 现在可以使用的功能

- 个人建档、五类自然语言记录、跨天补记、关键缺失追问。
- 自然语言纠错、按日期/类型/关键词查询、当日营养汇总和历史趋势。
- 根据基础档案自动填入可编辑的默认热量与营养目标；支持手动修改、恢复默认，再生成下一餐建议、次日重点和一周安排。
- 小幅目标变化自动生效；初次、单次或累计超过 5% 的变化需要确认；过时草案不会生效。
- 有证据的睡眠/摄入、工作日/周末规律；展示样本、窗口、覆盖率和限制，支持认可/否认。
- 根据完整饮食记录给出可确认的权重建议；手动调整权重和提醒时间。
- 日报、周报、后台站内提醒、数据导出、删除、超过一年后的月度归档。
- 服务重启后恢复记录与待追问事项；请求重试去重。

## 多用户改造进度

微信登录、按账号独立 SQLite 数据库、后台任务归属和并发额度控制已实现。服务只支持已登录用户；缺少微信 AppID 或 AppSecret 时启动失败。旧单用户数据已清空，不保留免登录模式和迁移入口。已增加应用内隐私授权、可撤回模型授权、账号注销和数据导出；部署与备份监控工具见 [阿里云上线操作手册](docs/阿里云上线操作手册.md)。尚未完成真实微信联调、异机备份及生产容量验收。

## 启动

环境要求：Python 3.11+、Node.js 22.12+。本次迁移在 Python 3.12.14、Node.js 24.15.0 验证。

首次在 Windows 运行 `.\setup.ps1` 安装后端和小程序依赖并构建，再运行 `.\start.ps1` 启动 API。后端健康检查为 <http://127.0.0.1:8000/api/health>，根路径不再提供页面。

先按 `.env.example` 配置 `WECHAT_APP_ID` 和仓库外的 `WECHAT_APP_SECRET_FILE`。macOS / Linux 可使用：

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.lock.txt
.venv/bin/python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --no-access-log
```

在 `miniprogram/` 执行 `npm ci`，正式构建前设置 `MINIPROGRAM_API_ORIGIN` 为真实 HTTPS 域名，再执行 `npm run build:weapp`；本机联调使用 `npm run build:weapp:dev`。微信开发者工具导入此目录并填入自己的 AppID。正式包不会读取设备中的开发地址覆盖配置，真机联调也需要手机可访问的后端地址。

正式使用需要 HTTPS 合法域名、开启微信登录并完成真实联调与部署验收。Python 依赖锁定在 `backend/requirements.lock.txt`，小程序依赖锁定在 `miniprogram/package-lock.json`。

## 模型配置与演示模式

模型配置由运行环境显式提供，源码不再包含 API Key。复制 `.env.example` 为 `.env`，配置 `MODEL_BASE_URL`、`MODEL_NAME` 和 `MODEL_API_KEY_FILE`（密钥文件放在仓库外）；开发模式也支持 `MODEL_API_KEY`，不能同时配置两种密钥来源。全部未配置时进入演示模式，部分配置缺失则启动失败。模型模式下，小程序自然语言内容会发送给配置的外部模型服务。

代码测试可以显式构造无模型配置的 `Settings` 进入演示模式。演示解析覆盖常见中文表达，页面明确提示其营养数值来自固定示例，不是完整或已核验的营养数据库。无法识别的食物保存为营养未知，不算成零。

演示模式可以验证这些表达：

```text
中午吃了一大碗牛肉面，加了一个卤蛋
不是大碗，是小碗
今天早上体重65公斤，昨晚睡了7小时
今天跑步30分钟，有点累
今天月经开始了
查看最近7天的饮食记录
我不喜欢燕麦
```

后端调用兼容 Chat Completions 的 `/chat/completions` 接口，用 Pydantic 验证结构化输出。首轮模型只收到本次输入、当前时间和操作状态，输出可包含多个任务的处理计划，不再默认发送最近 12 条记录。程序审核计划后，按固定视图取最少必要数据；模型不能选择任意记录 ID、SQL 或字段。密钥不会传到小程序客户端或数据导出。模型失败会明确报错，不悄悄切换到演示估算。

未另行同意模型授权时，请求携带 `processing_mode=local_only`，服务器统一禁止规划、纠错、营养估算、建议生成和润色等外部调用；缺失营养保持未知，不使用演示固定值。可在“我的 → 隐私政策与模型授权”同意或撤回模型处理；该限制随待补充流程保存，重启或恢复后不能通过 `model_allowed` 自动放宽。也可在 `.env` 中设置 `PROCESSING_MODE=local_only`，从服务端强制禁止外发。授权页显示供应商、模型、用途和数据类别，聊天页显示当前处理方式。模型模式下，调用结果还附带 `model_disclosures`，记录实际调用用途和数据类别，不含健康原文。详细规则见 [模型数据访问边界](docs/模型数据访问边界.md)。

模型负责输入理解、缺失营养粗估，以及选择本地批准的建议要点与反馈表达版本；统计、营养求和、权重建议、计划差异校验与写入边界由代码执行。自动化测试使用模拟响应，不会产生模型费用。

Chat 先提取允许缺少必需信息的草稿，再由本地检查完整性。例如“帮我记录昨天吃得有点咸”缺少具体食物时会追问，而不会因为空食物列表直接校验失败。补充答案只更新当前 `ClarificationTask` 批准的字段，保留首次解析的日期、原文和已知食物；草稿和追问任务随工作流持久化，重启后可继续。

饮食反馈单独提取 `salty/oily/overeating/hungry`（偏咸、油腻、吃撑、仍饿），保存用户原话、对应日期和自述/假设/否认标识。它是主观反馈，不是钠或热量已超标，也不会自动保存为长期偏好。补充食物和分量时保留当前工作流的关注点；只有日期匹配且可唯一关联的真实餐食才附带这份反馈。明确否认会撤回，其他新工作流不会自动继承。

单纯说“昨天吃得有点咸”，会先回应偏咸的关注点并提供小规模审核条目中的一般建议，再给出可选复盘问题；不知道、不想记录或转为咨询可以结束追问，不保存空餐食。“昨天吃得咸怎么办”直接进入咨询，不要求先填完记录。明确要求记录时，必需字段检查保持不变。前端区分可选补充与必需补充。

回复采用“结构化上下文 → 本地批准的选项 → 模型选择标识 → 本地校验与渲染”。公共输出策略位于 `backend/app/policy/output.py`。普通建议模型只返回 `point_ids`，反馈表达模型只返回 `point_id/variant_id`；日期、分量、热量、目标、保存状态、完整性、估算说明和追问由本地程序生成。偏咸与油腻的一般建议条目分别参考 [WHO 减钠](https://www.who.int/news-room/fact-sheets/detail/sodium-reduction) 和 [WHO 健康饮食](https://www.who.int/news-room/fact-sheets/detail/healthy-diet)，审核日期 2026-10-09；吃撑、仍饿只引导回顾体验，不诊断或生成补偿性节食建议。

表达校验检查严格 Schema、要点顺序/覆盖、建议在本次上下文中的可用性及重复项，拒绝自由正文、伪造状态、未知标识和额外字段。失败时使用同一上下文的本地表达，不影响已保存记录，也不切换演示营养。当前普通建议限于本地目录中的记录复盘、规律进餐与趋势观察，不能生成目录之外的新建议。普通记录不调用表达选择模型；已给出的建议不在每轮追问重复。追问选择先落 checkpoint，恢复时重新校验选择并生成本地问句，不重发模型请求，也不沿用旧 checkpoint 的自由正文。营养粗估器的自由误差说明不直接展示，由本地按来源生成未核验和误差提示。

聊天新增独立安全入口：`本地规则 → safety_classification 模型任务 → 本地校验与路由 → 操作权限检查 → 原有业务 → 输出前复核`。首次输入、追问原文（包括选择纠错记录时的附言）和计划备注都先检查。模型仅输出多风险标签、主体、否认/假设、时间及连续原文证据，不生成治疗方案或工具权限。紧急危险优先，其次为进食障碍/补偿行为、医疗问题、特殊人群及不确定风险。本地明确风险和已确认档案限制不能被模型的“普通”结果覆盖；本地词语规则偏保守，否认或假设中明确出现风险词时也可能触发边界。

安全分类单独经过现有发送授权、固定 Schema、字段白名单、单次授权消费和累计预算；HTTP 超时配置为 8 秒，每工作流最多 8 次分类调用，仍共享总调用/字节预算。只发送当前输入、同工作流必要原文、年龄和营养适用状态；显式承接前文时最多补一条同会话用户原文，不发送旧助手回复、完整档案或任意健康记录。引用原文会登记现有数据血缘。分类结果按输入、上下文、档案/实际安全限制及模型/策略版本指纹缓存，重放不重复调用；旧 checkpoint 缺少有效安全判断时拒绝继续敏感操作，需重新提交。第一版不新增长期风险状态或推断诊断。

风险、冲突、不确定、模型超时/预算耗尽或非法证据都使用本地固定安全回复；停止本次普通记录解析、营养估算、评分、建议和计划。此前已保存的独立记录保留并说明。模型判为普通后，本地仍在解析、估算、写入、回复和计划激活前核对限制；普通建议只能选择本地目录中针对当前视图批准的要点，日期、数值与来源说明由本地绑定。安全分类仍可能漏判，目录与业务规则仍需持续评测。

无模型或 `local_only` 时不伪装完成了语义分类：仅允许完整匹配本地白名单的原始记录、查询和已知食物偏好，关闭演示营养补值、餐食评分和附带建议；未消耗的文字一律按不确定处理。计划没有文字附言时无需语义分类，但仍检查已知限制和目标数值；手动目标仅支持本原型的 `1500–3500 kcal/天`、每周运动不超过 300 分钟范围，属于产品边界而非个体医疗安全阈值。

独立规则语料与语义语料位于 `backend/tests/fixtures/safety_*.json`。本地集成测试使用受控模型验证误放行后的独立保护、失败兜底、越权发送、追问/重启、计划绕过和输出检查；现有业务测试的模型桩通过 `safety_transport` 隔离新分类任务。真实模型评测脚本不读取用户数据库，运行方式：在 `backend` 目录执行 `python -m scripts.evaluate_safety --run --output ../docs/evidence/safety-evaluation.json`，会向已配置供应商发送合成语料。省略 `--run` 只验证语料。评测分别报告风险拦截召回、普通输入误拦截、分类失败、各类分支命中和延迟；小样本通过不代表临床验证。当前一次实测见 [安全分类评测报告](docs/evidence/safety-evaluation-2026-10-26.json)：10 条风险均拦截、6 条普通均放行，2 条首选分支与标注不同。

固定安全边界参考 [NHS 胸痛](https://www.nhs.uk/symptoms/chest-pain/)、[呼吸困难](https://www.nhs.uk/symptoms/shortness-of-breath/)、[NICE 进食障碍指南](https://www.nice.org.uk/guidance/ng69/chapter/recommendations) 和 [NIDDK 成人体重规划适用范围](https://www.niddk.nih.gov/bwp)，核对日期 2026-10-26。

普通咨询由处理计划申请固定视图：相关日期的饮食、近 7 天以内饮食汇总、近 28 天以内体重或分量上下文。用户明确要求更短窗口时只读取该窗口，超过视图上限时拒绝自动扩大。问“这顿”时，本地先绑定到选中记录或同一会话上一轮唯一结果；不明确就追问。单餐指代只发该餐的结构化内容；历史聊天原文和历史助手回复不发送。饮食建议可参考有条数上限的已确认偏好、限制和营养目标，分量建议还可参考必要基础档案；体重视图只包含日期和体重。模型新增上下文之外的数字、把未完整记录说成全天结论或给出诊疗结论时，回复会被拒绝并使用同一上下文的本地兜底。

只有完整且严格校验通过的记录才会写入健康数据库。混合输入中的完整独立记录可以先保存；未知分量可以保留为未知，但未知食物、体重/时长等必需信息不会写成空记录。回答“不知道”或“不记了”可结束当前补充。可选信息最多追问两轮，必需信息缺失不会因轮数达到上限而被强制保存。Qwen3.8-Max 的解析请求显式关闭思考模式，减少等待完整响应时超时的机会。

营养准备是独立的保存前节点，两条写入路径（追问期间保存独立记录、最终保存）共用它。解析仅提取用户提供的营养；食物与分量完整后，缺失营养再调用模型粗估。模型输出经数值范围、热量/营养素基本一致性及来源校验，记录保存营养状态、各字段来源、未知原因和对应食物/分量指纹。食物、分量或做法改变时重新估算，未变化的估算可复用；查看历史、查询、重试已完成请求不会触发补算。

用户提供的实际总量优先保留，缺少的字段可单独粗估；明确的每100g标签保存原值并按实际克数换算。更改分量后，旧的用户实际总量不会直接用于新分量，需要重新确认。模型失败或无法判断时仍保存食物与分量，营养保持未知并说明原因。未知分量不会假设为一份；当天有某项营养未知的食物时，不据已知部分计算该项剩余额度。模型热量的±25%范围只是示意误差带，不是经校准的置信区间。

营养准备结果随工作流持久化，提交后的重放不会重复估算。历史旧记录不会在读取时自动改写；可在历史页通过纠正记录触发营养准备。餐食卡片、回复中的热量说明和当日汇总均读取已保存的数值。

## Chat Graph v2 架构

聊天工作流采用“安全检查 → 理解输入 → 必要时追问 → 执行数据命令 → 组装回复”的固定流水线。模型只提出结构化处理计划和受限表达，本地程序负责批准数据范围、执行读写、检查版本和生成最终回执。

```text
backend/app/workflows/chat/
  graph.py                 节点顺序和路由
  safety_flow.py           安全入口
  interpretation_flow.py   理解输入、校验草稿
  policy.py                审核处理计划和数据范围
  clarification_flow.py    追问、暂停和恢复
  operation_flow.py        保存、纠错、查询和长期事实
  response_flow.py         查询回复、记录回执、建议和最终组装
  contracts.py             追问任务、操作命令和操作回执
  state.py                 Chat Graph 独立状态
```

信息不足时，系统保存一个明确的 `ClarificationTask`，记录正在追问哪条草稿、哪个字段以及是否必填。信息完整后，理解结果先转换成带版本的强类型 Command；命令不能自报权限，服务端按命令类型固定授权。ToolExecutor 在一个 UnitOfWork 中执行写入、幂等回执和数据来源登记；相同 `operation_id` 只有在规范化内容摘要一致时才能重放，不同内容会返回冲突。查询结果使用最小投影，回复模块只解释操作结果，不直接写数据库。

Chat 组件不再持有完整 `Engine`，而是分别获得只读 facade、受限运行时或 ToolExecutor。`Engine` 只负责组装公共服务；请求幂等、checkpoint、会话锁、取消、过期和删除后的写回保护仍位于 `workflows/runtime.py` 与 `workflows/concurrency.py`。详细设计见 [Chat Graph 模块化实现 v2.0](docs/chat_graph_模块化实现v2.0.md) 和 [统一类型化工具接口开发方案](docs/统一类型化工具接口开发方案.md)。

## 使用顺序

1. 建立基础档案，在对话页记录一餐和身体状态。
2. 分量缺失时回答追问；如果暂时不知道，直接说“不知道”。也可以取消或另开一条记录。
3. 在历史页查询和纠正记录；日期默认按上海时区解析，睡眠记录按入睡日期归属。
4. 建档后，计划页自动填入可编辑的系统默认目标，也可填写专业建议或自定目标。首份草案确认后生效；已有生效目标优先保留，点“恢复系统默认”才重新采用当前估算。期望日期不会直接转成节食强度。
5. 当天饮食全部记录完成后，点击“确认今日饮食已记录完整”。只有完整且营养信息齐全的日期用于摄入规律分析。
6. 持续积累数据，生成周复盘；数据不足时不会强行生成规律。

用户提供包装营养信息时，可用“午餐喝了一杯牛奶，热量120kcal，蛋白质8克，碳水12克，脂肪4克”。这代表实际食用份量的总营养，不是每 100g 数值；多食物或复杂标签建议接入真实模型并检查记录。

## 默认目标的依据与边界

`GET /api/targets/default` 是只读、本地计算接口，不调用模型，也不会自行激活计划。使用当前保存的档案（不是自动用某次体重记录替换档案）：年龄、身高、体重、男性/女性公式系数和活动水平。静息能量使用 [Mifflin–St Jeor 原始研究](https://pubmed.ncbi.nlm.nih.gov/2305711/)：`10×体重kg + 6.25×身高cm − 5×年龄 + 系数`，男性系数 `+5`，女性系数 `−161`。

活动系数按久坐/轻度/中等/较多设置为 `1.4/1.6/1.8/2.0`，是参考 [NIDDK 活动水平](https://www.niddk.nih.gov/bwp) 范围的粗略产品分档，不是实测消耗。目标体重更低时，初始缺口为维持估算的 10%，最多 300 kcal/天；目标相同或更高时只提供维持估算，不自动制定增重方案。不根据目标日期倒推，也不保证按期达到体重。

缺口、BMI自动估算范围及 `1500–3500 kcal/天` 处理区间是本原型的保守产品规则，不是统一临床阈值或个体安全保证。低于下限时仅在维持估算本身达到下限的情况下缩小/取消缺口；超出范围时不生成默认数值。减重目标按 50 kcal 单位向上取整，不会因取整额外扩大缺口。

宏量营养素初始采用蛋白质 20%、碳水 50%、脂肪 30%，按 `4/4/9 kcal/g` 换算并取整；比例只是 [成人参考范围](https://www.canada.ca/en/health-canada/services/food-nutrition/healthy-eating/dietary-reference-intakes/tables/reference-values-macronutrients.html) 内的产品起点，不是个体最优比例。每周运动默认 150 分钟，参考 [WHO 一般成人中等强度活动建议](https://www.who.int/europe/publications/i/item/9789240014886)，同样允许修改。

通用公式自动估算只覆盖原始研究中的 19–78 岁范围；性别系数不明确、当前 BMI 低于 18.5 或达到 40、目标 BMI 低于 18.5、孕期/哺乳期/特殊医疗营养需求或已记录专业限制时，不自动生成通用目标。未说明营养适用情况时会提示采用前核对，而不会声称已经核验适用。命中安全限制时，手填目标也不能用于生成通用计划。默认值不是精确测量或医疗处方。

计划保存目标来源、公式版本、估算依据和资料指纹。默认表单提交时重新核对数值与指纹，资料或限制变化后不能沿用旧估算版本；草案提出后资料变化会使确认过期。修改表单后按手动目标处理，刷新估算不覆盖未提交编辑或已有生效目标。计算依据与参考链接可在计划页展开查看。

## 数据与提醒

`data/health.db` 保存健康事实；`data/checkpoints.db` 保存 LangGraph 工作流进度。运行数据库含个人记录，应保留在本地；`.env` 被 Git 忽略。每条记录有发生时间、创建时间、修订版本和营养来源。数据库自动迁移到版本 6，迁移本身不会删除业务数据。

记忆分为工作记忆、事件账本、结构化长期事实与派生结果四层。待补草稿和待确认计划默认闲置 7 天过期，已完成流程上下文保留 30 天；过期后保留最小请求凭据，旧请求不能重复写入，已保存事件继续保留。可通过 `CONTEXT_PENDING_DAYS`、`CONTEXT_PLAN_DAYS`、`CONTEXT_COMPLETED_DAYS` 分别配置。清理中断可在下一次维护或服务重启后继续。

设置页支持新增、修改、撤回、选择冲突事实、查看长期信息变更记录与隐私删除。普通偏好明确改口后替代旧偏好，临时偏好不会静默覆盖长期偏好；未来日期的信息到期才生效。过敏和专业限制到期后进入待核对状态，继续保留现有保护。用户确认仅表示明确陈述，用户转述专业建议未经独立核验；旧自由文本保留为历史类型，不自动猜测结构。

历史记录可以展开修订历史和前后差异。规律、复盘、计划与月度摘要附带方法版本、窗口、生成时间及来源版本；来源变化、方法升级或窗口过期会显示更新/复核提示。历史复盘保留原统计窗口，已确认目标不会被自动改写；归档摘要不能承诺重新计算。详细约定见 [四层记忆实现说明](docs/四层记忆实现说明.md)。

删除事件或长期信息前，小程序先请求实际影响范围，分别列出需要删除、清除共享原文和保留独立目标的对象数量。程序记录实际读取的来源、版本、查询范围和原文副本，不把展示用 `evidence_refs` 当作完整依赖。只清理受影响的聊天、复盘、规律、通知、回执和流程进度；可证明独立的记录与流程继续保留。共享原文按已验证的字段片段重新绑定，所有修订一并处理；新记录也只保存最小证据片段。

历史数据缺少血缘时会明确扩大预览范围：可独立验证的健康记录只清除原文副本，不能验证的历史记录和长期信息可能需要一并删除。清理范围变化后必须重新确认。旧请求不能重新生成已删除内容，正在运行的相关模型结果也不能写回。清理使用持久化作业；数据库忙或 checkpoint 清理失败时显示未完成，可以继续清理，服务重启会先恢复作业再开放数据。

归档在同一个业务库事务中保存已校验的完整过期月份摘要并清理原记录，再清理相关 checkpoint；边界月份待整月过期后处理。摘要登记来源关系；通过原事件 ID 显式删除已归档事件时，会删除包含其贡献的月度摘要。详见 [精准删除与数据血缘解决方案](docs/精准删除与数据血缘解决方案.md)。

删除完成会清理 SQLite 页和 WAL。应用不自动创建备份；用户自行导出的文件或复制到其他位置的数据库不在应用清理范围内。超过一年后的摘要无法恢复逐餐细节，也不能用来精确复核逐日相关性。

后台每分钟检查站内任务。小程序关闭时服务仍可生成消息，下次打开后查看；当前没有设备级推送。服务停止期间不会实时提醒，重启时补生成最近七个有记录日期的日报。站内提醒允许关闭，记录允许跳过。

## 可观测性与健康数据保护

运行日志只记录固定事件、耗时、结果和服务端关联 ID，保存在 `DATA_DIR/observability/`，总大小最多 30 MiB，保留最近 7 个 UTC 自然日。健康原文、prompt、模型响应、SQL 参数、凭据和异常原文不进入该出口；默认关闭 thread 关联和业务质量指标外发。LangGraph 执行显式关闭第三方内容 tracing。

营养未知率、必需追问率、记录纠正率及计划处理结果通过业务库中的事务账本统计，重放不重复计数，删除同步清理；窗口为最近 30 个上海自然日。数据库迁移到版本 9，不回填推测的旧指标。

内部指标默认关闭。本机需要时设置 `OBS_METRICS_ENABLED=true`，从回环地址访问 `/internal/metrics`；只有再设置 `OBS_QUALITY_EXPORT_ENABLED=true` 才包含质量聚合。加固网关拒绝 `/internal/`，不会自动对宿主机或公网开放指标。`OBS_ENABLED=false` 关闭运行遥测，质量账本仍随业务事务维护。

完整配置、统计口径及验收见 [可观测性与健康数据保护开发方案](docs/可观测性与健康数据保护开发方案.md)。合成性能验证入口为 `python scripts/benchmark-observability.py`，仅创建临时数据库，不读取个人数据。

## 运行环境加固

直接运行 `start.ps1` 属于本地开发模式，没有操作系统级沙箱。开发模式同样启用完整请求体 64 KiB、接收总时限10秒、模型响应1 MiB、全局2个活跃工作流和默认120秒执行期限。

单机 Linux 容器部署配置位于 `compose.hardened.yaml`：非 root、只读代码和依赖、独立数据卷、限额临时目录、受控 HTTPS 出口代理与容器资源配额。模型密钥从只读秘密文件注入；容器启动不安装依赖，不挂载开发目录或个人主目录。基础镜像使用可访问的 Docker Official Images 公共镜像并锁定 digest。

Windows 检查入口：`powershell -File scripts/start-hardened.ps1 -SecretFile C:\private\qingji-model-key.txt`。它不会回退到本机 Python；首次创建独立命名卷，不自动导入个人数据库。先完成 [网络策略](deploy/network-policy.md)、[独立监督](deploy/health-supervision.md) 与实际探测，再接受加固部署。Windows Docker Desktop 的宿主机网络隔离尚需单独验收。

检查命令：`python scripts/verify-runtime.py --project qingji-hardened --output output/runtime-verification.json`。报告只含配置/权限/配额与合成探测结果，不读取个人数据库；未验证项保持未验收。配置文件存在不代表所有隔离项通过。

完整设计、限制与验收条件见 [运行环境最小权限修复开发方案](docs/运行环境最小权限修复开发方案.md)。迁移前停机并一致性备份两份 SQLite 数据库及必要 WAL，不允许本机与容器服务同时操作同一数据目录。原源码密钥必须在供应商侧撤销并更换，移除源码不会自动撤销密钥。

## 后台任务与恢复

日报、周报、归档和提醒使用持久化任务表；领取执行、续租、失败重试和结束状态带有执行凭证。每轮扫描只规划待办，后台并发为 1，各任务独立使用运行额度。周报通过 outbox 创建幂等计划任务，继续遵守计划确认与隐私删除规则。

当前仍只支持同一数据目录一个 Engine，进程在数据库初始化前取得 OS 文件锁。不要添加多个 Uvicorn worker，也不要让本机与容器同时使用同一数据目录。关闭通知后，报告计算继续，站内提醒停止；失效提醒不会跨窗口补发。

`SCHEDULER_ENABLED=false` 停止规划新周期任务，`JOB_RUNNER_ENABLED=false` 停止后台领取。`GET /api/jobs/status` 提供脱敏的队列数量、失败任务编号及最近规划时间。配置项见 `.env.example`。

离线管理前先停止服务，在 `backend` 目录执行以下命令（数据目录必须指向需要管理的目录）：

```powershell
..\.venv\Scripts\python.exe -m app.jobs.manage --data-dir ..\data --user-id 内部账号ID status
..\.venv\Scripts\python.exe -m app.jobs.manage --data-dir ..\data --user-id 内部账号ID pause
..\.venv\Scripts\python.exe -m app.jobs.manage --data-dir ..\data --user-id 内部账号ID resume
..\.venv\Scripts\python.exe -m app.jobs.manage --data-dir ..\data --user-id 内部账号ID retry TASK_UUID --reason upstream_recovered
```

`pause` 持久化停止领取，重启服务后仍保持暂停，`resume` 解除。重试仅接受未过期且来源有效的 failed 任务，并记录操作原因。管理命令不发送模型请求；运行中的数据目录会拒绝离线管理。升级至 schema 8 后，旧二进制不能直接打开新数据库；回滚需要停服恢复成对备份。

方案、任务状态和故障验收见 [调度器可靠性与独立 Worker 开发方案](docs/调度器可靠性与独立Worker开发方案.md)。本次实施 A 期；独立 Engine 运行服务和多实例扩容属于后续阶段。
